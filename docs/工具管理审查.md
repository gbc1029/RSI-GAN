四、实证发现的新问题（四份文档均未记载）
P1【高】register/unregister 的补丁必然 apply 失败（换行根因）
链条：仓库 4 个注册表 JSON 末尾都带 \n（实测）→ 两工具用 json.dump(..., indent=2) 重写 workspace 副本，不带 \n（register_component.py:130-131、unregister_component.py:80-81）→ gan/patch.py 用 difflib.unified_diff，它不输出 \ No newline at end of file → 注册表 chunk 的最后一个 + 行失去行终止符 → 单 chunk 时 git apply 报 corrupt patch；多 chunk（如 unregister 附带删模块文件）时污染后续 header，报 patch fragment without header → patch -p1 兜底同样失败（code_repo.apply_patch:244-253）→ PatchRejected("patch failed to apply")，会话内 patch_retry_k 重试每次重建同样的坏补丁。
实证：真实注册表内容 + register_component("probe") → patch 生成正常（232 字节）→ apply_patch: False（git apply: corrupt patch at line 14）；unregister_component 同样失败。对照组：普通 edit_source str_replace 修改 .py → apply 成功。
推论：deep 注册/注销自实现以来从未能真正提交过；文档的“提交门控集成测试（5 例）ALL PASS”未覆盖真实 apply 链（属验证缺口，正是 docs/7 §9 担心的类型）。修复本身很小（写末尾换行或让 patch 生成器 newline-safe），但现状使身份闭环的“写接口”整体失效。
P2【高】build_patch_from_workspace 静默丢弃未被 grant 的新建文件
patch.py:50-53：只遍历 granted 的 rel 路径，且 if not os.path.exists(a_root): continue——agent 用 edit_source create 新建的文件（不在 grant 记录里）不会进入补丁。
实证：grant 具体文件 → 同目录 create 新组件文件 → 会话补丁长度 0（新文件静默蒸发，无任何报错/事件）。
加重因素：list_editable 明确引导“只传具体文件路径、不要 glob”（list_editable.py 描述 + expand_roots 只返回 isfile 项），而只有 grant 目录 新文件才会被捕获（实证 dir-grant 时补丁含新文件）。
P3【高】deep-add 三重死锁，register_component 在其主用途上不可用
register_component 第 2 步只查 code_root 是否有该模块（register_component.py:88-90），新文件只在 workspace → 报 "module not found... Create the file first"（误导：文件刚建好）；
list_components/unregistered 同样只扫 code_root（list_components.py:63,69-70）→ workspace 新文件不可见；
即使补丁带上新文件，提交门控按“新增孤儿”打回（code_repo.py:361-366），而打回提示让 agent 去 register_component——回到第 1 条，会话内无解。
实证：三步全复现。文档宣称的闭环（impl 文档 §6 步骤 1-4、identity 文档 §3.2）不成立。当前唯一可行路径是绕开 register_component、手工 request_source_access(gan/registries/task.json) + edit_source str_replace 编辑注册表 JSON（实证该路径可通过提交门控）——而 P1 保证的“手工 str_replace 保住换行”恰好不受影响，形成“专用工具不可用、土办法能用”的倒挂。
register_component 仅剩的用途是给“既存未注册文件”补登记，但提交门控会阻止这类文件进入代码树，当前仓库也不存在这种历史孤儿——该工具现状实际无用武之地。
P4【中】重复 grant 覆盖 workspace 未提交编辑——只修了 register 一处
AccessBroker.grant 仍无条件 re-copy（access.py:150-153）。identity 文档只在 register_component 内做了 if not os.path.isfile(ws_reg) 守卫（:113）；unregister_component.py:64,66 与 request_source_access.py:39 仍会覆盖。agent 在会话中先改完某文件、再次 request_source_access（如扩大授权面时把旧路径又列进去）→ 编辑被静默还原。文档只记录了 unregister 一例，request_source_access 这条主修改通道的同类风险未被登记。

P5【低】planner 对 shared.json 的跨角色写权
frozen.py：planner 写根含 gan/registries/shared.json 与 gan/components/shared/** → planner 可 register_component(registry="shared.json")（schema 枚举里也提供了）把组件暴露给所有角色，也可 unregister 掉 bash/editor 波及全角色。review 文档 §1.7 提过 unregister 侧，register 侧 + register_component 枚举显式提供 shared.json 的组合未被记录。
