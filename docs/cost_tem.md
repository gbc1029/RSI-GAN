# 定义约定
cost包含：token消耗（主），时间消耗（次），工具调用次数（再次）
一切讨论的 "被管理的上下文"都是经过了可见范围筛选和脱敏的，即原完整注入、通过上下文管理方法筛选,权限上agent完全可见
roles必须有源码级的修改权限，不能仅在配置的极少数选项中选择


# 初步设计
需要融合以下设计而非选其中一项；可以在以下设计的基础上提出改动

## 成本参数
把成本直接相关的执行参数从 CLI/loop.yaml 下沉为 design 键：
per-question 预算、tool-call 上限、知识物化上限，以及模型思考强度（不开放：num-sample;模型选择）
需要新增“保留键”：框架预声明、框架消费、消费点钳制，不受当前“键必须有消费者”检查

## "select trajectory"优化
开放 控制read trajectory背后的过滤 的权限

1：提供default / slice 两种模式选项，default即当前模式，slice下read trajectory改为返回索引，agent根据索引挑选重点内容查看详情。大部分情况下后者更优，并不能提供足够的进化空间
2：添加供roles自定义的select_trajectory步，使read trajectory时经过权限过滤和select_trajectory取并集。实际上read trajectory本就属于可被编辑源码的部分（直觉推断，需要审查），添加select_trajectory只是一个显式的接口。select_trajectory进行筛选是否需要提前建立索引，还是由roles自进化？

问题：如何划分索引、如何使trajectory可被充分管理

筛选模式：
语义匹配筛选目前没有相关embedding，且也是query与trajectory匹配，而非当前语境与trajectory匹配，同“不可进化的设计”无区别
正则式筛选/硬条件筛选：在单domain不同题/多domain情况下，是否可能达成有效筛选？
memRL式：需要根据“任务是否成功”进行RL式记忆加权，需要较多数据量
根本问题：单次read trajectory可及的数据量（最多是前几代指定agent的运行轨迹）无法支撑复杂的筛选逻辑

## 直接文本反馈
仅做成本反馈和简易的“约束成本”的提示词要求。实现相对简单，且是其他的基础

inner：通过e的eval-point进行反馈，只能评估t；
outer：在self-improve中注入成本反馈：

可见范围问题：
空间维度：对每个会话的成本数据可读范围分配，仅看自己有权管理的内容（及当前会话？）
时间维度：近几代的成本数据，考虑如何划分；仅成本数值、无实际内容（如轨迹信息、配置信息乃至源码）不足以支撑修改决策，考虑如何把控边界

精细度问题：
信息传递粒度：是否精细到每一次LLM调用和每一次tools调用？
信息注入精度：每会话传递一次被管理的信息，还是在会话中实时可见当前会话的成本?

注入的信息需要能支撑决策和修改，但是不能过于冗余


## 独立“上下文管理”项
独立于tools，需进一步设计
select_trajectory理论属于context_manager的子集，考虑是否将其统一

以下初始设计需要进一步融合：
自由设计：
context_manager(state),
state即任务、当前步骤、历史轨迹、可用上下文块、工具输出、预算、已用成本、任务类型等全部可见信息（经过脱敏和可见范围筛选），context_manager内部自由设计，然后再将返回值交给LLM
约束设计：
提供一组上下文操作原语（实际呈现为被调用的函数，必须包括足够广泛的操作才能保证进化空间），P/E 只能排列、组合、条件判断、应用这些原语
分层设计：
将context_manager作为可配置项，提供浅层选择通道；并开放深层源码级修改
