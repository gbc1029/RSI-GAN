# 拆分仓库方案（task / roles / base）

> **状态**：设计稿（未实施）
> **编写时点**：HEAD = `1669933`（`main` 与 `heal` 同指）
> **关联问题**：outer self-improve 的代码改动只落在当前分支；下一 outer 的 `_align_code_base(parent)` 会 checkout 父代 `code_commit`，导致角色代码被一起回滚。见 `docs/7_遗留问题与待办.md` §6 与 `docs/整合_待办记录.md` §6。
> **关联约束**：`gan/framework/frozen.py` 的 `TASK_SOURCE` / `PLANNER_SELF` / `EVALUATOR_SELF` / `SEAT_WRITE`。

---

## 1. 背景与问题

### 1.1 现象

- 角色代码（`gan/roles/{planner,evaluator}.py`、`gan/tools/work/<role>/**`、`gan/components/<role>/**`、`gan/registries/<role>.json` 等）与任务代码放在**同一棵 git 树**（`code_root`）。
- outer self-improve 的改动通过 `_apply_self_patch` 提交到**当前 HEAD**。
- 下一 outer 的 `_align_code_base(parent)` 调用 `checkout_base(code_root, parent.meta["code_commit"])`，把**整棵树**切到父代任务提交。
- 父代任务提交不含角色 self-improve commit ⇒ **角色代码被 rollback**。

### 1.2 影响

- 设计配置（prompt/params/tool 选择）存在 `ckpt/design/`，不受影响；
- 角色**代码**（新增/修改的工具、组件、注册表）会丢失或被替换成旧版本；
- 设计仍引用某工具、但代码已不在当前树 ⇒ 装配期 skip（有报告，但能力静默缺失）；
- `_role_commits` 目前只记录/存档，**没有任何地方重新应用**（`loop.py` 仅 init / state / load / assign 四处引用）。

### 1.3 根因

**角色代码与任务代码共用一棵 git 树，且父代对齐是树级的 checkout。**

---

## 2. 目标与不变式

**目标**：任务分支切换（`_align_code_base`）**绝不能碰到角色代码**。

**不变式**：

1. **仓库边界 = allowlist 边界**：仓库划分直接对齐 `frozen.SEAT_WRITE`。
2. **角色仓库只随 outer 前进**，从不被 task 分支 checkout。
3. **冻结 base 单一来源**：`gan/framework/**`、`agent/`、`utils/`、`domains/` 在所有执行视图中都来自同一个 base。
4. **每个 seat 的写集恰好落在一个仓库**（见 §4），因此单个会话产出的补丁只针对一个仓库。

---

## 3. 仓库划分

### 3.1 基线：2 个可进化仓库 + 1 个冻结 base

| 归属 | 路径 | 谁写 |
|---|---|---|
| **base（冻结）** | `gan/framework/**`、`agent/**`、`utils/**`、`domains/**`、`task_agent.py`（初始版）、`gan/tools/work/common/**`、`gan/tools/design/**`、`gan/tools/deep/**`、`gan/tools/assembly.py`、`gan/roles/base_role.py`、`gan/design/{__init__,schema,store}.py`、`gan/registries/loader.py`、`gan/build.py`、`gan/summary.py`、`gan/driver.py`、`gan/__init__.py` | 无 |
| **task 仓库** | `task_agent.py`（若演化）、`gan/components/task/**`、`gan/registries/task.json`、`gan/design/schema_ext/task.json` | planner 的 `plan` seat |
| **roles 仓库** | `gan/roles/planner.py`、`gan/roles/evaluator.py`、`gan/tools/work/planner/**`、`gan/tools/work/evaluator/**`、`gan/components/planner/**`、`gan/components/evaluator/**`、`gan/registries/planner.json`、`gan/registries/evaluator.json`、`gan/design/seeds/{planner,evaluator}.md`、`gan/design/schema_ext/{planner,evaluator}.json` | planner/evaluator 的 `self_improve` seat |

> 这张表直接由 `frozen.py` 的 `TASK_SOURCE` / `PLANNER_SELF` / `EVALUATOR_SELF` 导出。

### 3.2 可选细化

| 方案 | 内容 | 取舍 |
|---|---|---|
| **2 仓库（基线）** | task + roles | 改动适中，推荐先做 |
| **3 仓库** | task + planner + evaluator | 角色版本完全独立（planner/evaluator 各自回滚互不影响）；plumbing 更多 |
| **简化版** | 保留 2 仓库，但把 `gan/roles/{planner,evaluator}.py` 移回 base 并冻结 | 消除 `gan/roles` 包跨仓库的导入问题；代价是这两文件不再可自改 |

## 4. 关键事实：seat → 单仓库

| role / seat | 写集（`frozen.SEAT_WRITE`） | 目标仓库 |
|---|---|---|
| planner / `plan` | `TASK_SOURCE` | **task** |
| planner / `self_improve` | `PLANNER_SELF` | **roles** |
| evaluator / `self_improve` | `EVALUATOR_SELF` | **roles** |
| evaluator / `evaluate` | `[]` | 无 |
| task / `task` | `[]` | 无 |

**推论**：单个会话产出的补丁只针对一个仓库——补丁构建、校验、应用、提交都不需要跨仓库合并。这是拆仓库方案能保持干净的根本原因。

## 5. 目录与初始化

### 5.1 目录布局

```
<output_dir>/ckpt/code/
├── base/                 # 冻结快照（只读；可为 base 仓库/软链）
├── task/                 # git 仓库
│   ├── .git
│   ├── task_agent.py     # 仅当演化过才存在
│   └── gan/
│       ├── components/task/**
│       ├── registries/task.json
│       └── design/schema_ext/task.json
└── roles/                # git 仓库
    ├── .git
    └── gan/
        ├── roles/{planner,evaluator}.py
        ├── tools/work/{planner,evaluator}/**
        ├── components/{planner,evaluator}/**
        ├── registries/{planner,evaluator}.json
        └── design/seeds/*.md
            design/schema_ext/*.json
```

### 5.2 初始化

替换 `gan/build.py:ensure_code_root`：

1. 从 run 起始仓库生成 `base/`（只读快照）；
2. 用 base 中属于 task/roles 的路径做初始文件，分别建两个 git 仓库；
3. 各打一个 initial commit；
4. 写入 `ckpt/code.json` 清单（见 §11）。

> 仓库目录里**只放可进化文件**；base 共享一份，避免重复复制整个 repo。

## 6. 运行时组合视图（composed view）

### 6.1 问题

`gan/roles/planner.py` 在 roles 仓库，`gan/roles/base_role.py` 在 base；Python 需要 `gan/roles` 包完整。`gan/components/<role>`、`gan/design/...` 同理。

### 6.2 方案：每个 outer 物化一个组合视图

- `runtime_root(role, outer)` = base 目录树 + 对应仓库内容**按路径覆盖**后生成（symlink farm 优先，copy 兜底）；
- 覆盖顺序：`base` → `task`（仅 planner/evaluator 读）→ `role 仓库`；
- 角色进程与 task 沙箱都从组合视图执行；
- 仓库 tip 变化时重建（outer 开始 / self-improve 提交后）。

**不建议**直接靠 `PYTHONPATH` 叠加：多个 `gan/__init__.py` 会让 Python 只认第一个包，子包无法合并。物化视图语义明确、可审计。

## 7. Root 路由

新增 `RepoRoots` 抽象：

```
roots = {
  "base":      <base root>,
  "task":      <task repo root>,
  "planner":   <roles repo root>,   # 3 仓库时为 planner repo
  "evaluator": <roles repo root>,   # 3 仓库时为 evaluator repo
}
```

两个核心函数：

1. `owner_repo(rel)`：按 `TASK_SOURCE` / `PLANNER_SELF` / `EVALUATOR_SELF` 匹配，返回仓库名；否则 `base`。
2. `resolve_read(rel)`：按覆盖顺序找第一个存在的仓库文件（base 兜底）。

`gan_roots` 从"单根三元组"改为**按 role 返回三元组**：

| role | tools_dir | registry_dir | components_dir |
|---|---|---|---|
| task | base `gan/tools` | task 仓库 `gan/registries` | task 仓库 `gan/components` |
| planner | base `gan/tools` + roles `gan/tools` | roles `gan/registries` | roles `gan/components` |
| evaluator | 同上 | 同上 | 同上 |

`gan/registries/loader.py:load_registry_for_role(role, registry_dir, components_dir)` 接口不变，按 role 传入正确目录即可。

## 8. 访问 / 工作区 / Broker

- `gan/framework/access.py:AccessBroker` 从"一个 `code_root`"改为"一个 `RepoRoots`"；
- `grant(role, node, paths, ...)`：每条路径用 `owner_repo` 解析，从对应仓库复制到 workspace；grant 记录增加 `repo` 字段；
- `workspace.src_dir` 保持单目录，但每个文件记录来源仓库（供补丁构建分组/归因）；
- `frozen.is_allowed` 不变（仍是相对路径），写目标由 `owner_repo` 决定；
- `clear_workspace` / `_resync_workspace` 保持，复制源按仓库解析。

---

## 9. 补丁构建 / 应用 / 提交 / 血缘

由于每个 seat 只写一个仓库：

- `gan/patch.py:build_patch_from_workspace(broker, role, key)` 增加目标仓库参数（由 seat 推导：`plan`→task，`self_improve`→role repo）；
- 只对该仓库的 working tree 做 diff；
- `code_repo.check_patch` / `apply_*` / `current_commit` 全部改为按仓库调用；
- `code_repo._TREE_LOCK` 改为**每仓库一把锁**（planner/evaluator 自改可并行；task 补丁与它们不冲突）；
- 节点 meta 与 loop state 记录：

```
task_commit, planner_commit, evaluator_commit
```

（2 仓库基线可记录 `task_commit` + `roles_commit`，再按 role 拆分审计字段。）

- `code_lineage` 事件同步输出 `task_base`（及可选的 role commit）。

---

## 10. 对齐：`_align_code_base` 只 checkout task 仓库

- `gan/framework/loop.py:_resolve_base(parent)` 继续取 `parent.meta["task_commit"]`（字段改名，语义不变）；
- `_align_code_base` 调用 `checkout_base(task_repo, base)`，**只作用于 task 仓库**；
- roles 仓库**不参与 checkout**，只由 self-improve 提交推进；
- `outer_base_ref` 改为 task 仓库的 ref；
- 若后续 outer 选择需要回溯历史角色版本，单独提供 `checkout_role_repo(role, commit)`，与 task 对齐解耦。

---

## 11. Checkpoint / Resume

`ckpt/code.json` 从单 commit 扩为清单：

```json
{
  "base":    {"version": "<run 起始版本/commit>"},
  "task":    {"repo": "ckpt/code/task",  "commit": "..."},
  "roles":   {"repo": "ckpt/code/roles", "commit": "..."},
  "planner": {"repo": "ckpt/code/roles", "commit": "..."},
  "evaluator": {"repo": "ckpt/code/roles","commit": "..."}
}
```

- `gan/framework/checkpoint.py:save_checkpoint` 逐仓库取 `current_commit`；
- `restore` 逐仓库 checkout；
- `reconcile_refs` 逐仓库；
- 任一仓库不完整/不可解析 → `RepoIntegrityError`（保持现有 fail-fast 语义）；
- `enable_checkpoint=false` 时同样不写清单。

---

## 12. 预检 / 装配 / 沙箱

- `preflight_tools`：按 role 从正确仓库读 registry/components；碰撞检测在**组合视图**上做；
- `repair_dangling_designs`：role 设计对 role 仓库，task 设计对 task 仓库；
- `assemble_tools_dir_reported`：always-on 从 base（`work/common`、`design`、`deep`）+ role 仓库（`work/<role>`）组合；组件从 role 仓库；
- **task 沙箱**：只拷 base + task 仓库的最小允许清单，**绝不拷 roles 仓库**；
- **角色进程**（`gan/framework/role_process.py`）：从组合视图运行，包含 base + 对应 role 仓库 + 只读 task 视图；
- AST / 能力门：提交门按目标仓库执行；框架 plumbing 豁免规则不变。

---

## 13. 迁移与双模式

用开关 `code_layout: single | split` 过渡：

1. **single**：现有行为，读 `ckpt/code` 单仓库；
2. **split**：新行为；
3. **旧 checkpoint 迁移**：把 `code.json` 的单 commit 视为 `task_commit`；roles 仓库用当前磁盘上的角色文件（或 base 种子）初始化并提交，记录一条 `migration_event`；
4. 迁移只做一次，之后固定 split。

## 14. 测试计划

| 测试 | 断言 |
|---|---|
| **拆分不串味** | task 补丁只改 task 仓库；role 补丁只改 roles 仓库 |
| **对齐不碰角色** | `_align_code_base` 到旧 task 父代后，roles 仓库 working tree 与提交不变 |
| **self-improve 不丢** | outer N 的 role commit 在 outer N+1 的任意 task 分支下都可见 |
| **组合视图** | `gan/roles/planner.py`（roles）+ `base_role.py`（base）可同时导入 |
| **装配** | planner 工具来自 roles、common/design/deep 来自 base、task 工具来自 task |
| **checkpoint** | 三个 commit 全部落盘、resume 后一致 |
| **沙箱** | task 沙箱不含 roles 仓库任何文件 |
| **并行** | planner/evaluator self-improve 不再争同一把树锁 |
| **回归** | `scripts/local/run_tool_regression.py`、frozen 布局检查、deep/batch 套件全绿 |

## 15. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **`gan/roles` 包跨仓库** | `planner.py` 在 roles，`base_role.py` 在 base | 物化组合视图；或采用"简化版"把 role 入口冻结在 base |
| **`task_agent.py` 双身份** | 既是 base 运行时又在 `TASK_SOURCE` | 覆盖规则：task 仓库有则优先，否则 base；沙箱按组合视图取 |
| **seeds / schema_ext 跨仓库** | `gan/design` 下部分文件属 role | 物化视图；`owner_repo` 精确匹配 |
| **组合视图成本** | 每 outer 物化一次 | symlink farm（便宜）；只在 tip 变化时重建 |
| **存储** | 多仓库 | base 单份只读；仓库只放可进化文件 |
| **旧 checkpoint** | 单 commit 格式 | 一次性迁移 + 事件记录 |
| **审计** | 三 commit 的血缘 | 节点 meta 与 `code.json` 同时记录；事件输出 |
| **并发锁粒度** | 多仓库多锁 | 按仓库加锁；跨仓库只读不阻塞 |

---

## 16. 实施顺序（建议）

| 阶段 | 内容 | 产出 |
|---|---|---|
| **0** | 加 `RepoRoots` / `owner_repo` / `resolve_read` 抽象，但先只接一个 root | 无行为变化，铺路 |
| **1** | `ensure_roots` 建 base + task + roles；`code.json` 清单化 | 结构就位 |
| **2** | `_align_code_base` 只 checkout task；self-improve 提交 roles | **核心问题解决** |
| **3** | broker / workspace / patch / commit 按 seat→repo 路由 | 读写正确 |
| **4** | 组合视图 + `gan_roots(role)` + 装配/预检 | 运行时正确 |
| **5** | checkpoint/resume 三 commit；迁移 | 可恢复 |
| **6** | 沙箱裁剪 + 并行锁 + 回归 | 收尾 |

---

## 17. 非目标

- 本文档不改变 inner/outer 的**选择算法**（锦标赛 / novelty / MAP-Elites），只解决"角色代码被任务分支 rollback"这一结构问题；
- 不改变 `frozen.SEAT_WRITE` 的授权语义；
- 不引入 crossover；
- 不处理多域评测（`docs/9`）。

---

## 18. 一句话

**仓库边界就用 `frozen.SEAT_WRITE` 的边界**：task 仓库归 `plan` seat，roles 仓库归两个 `self_improve` seat；`_align_code_base` 只 checkout task 仓库，roles 仓库只随 outer 前进。这样补丁永远是单仓、self-improve 永不被 rollback，代价是引入"组合视图 + Root 路由 + 多 commit 血缘"三处 plumbing。
