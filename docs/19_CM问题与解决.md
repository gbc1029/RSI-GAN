## 1.5 判断口径与威胁模型（讨论新增）

本节记录本轮讨论形成的判定标准；具体应用写在每个问题的“判断”段。

### 1.5.1 三类问题性质

| 类型 | 定义 | 判据 | 典型归属 |
|---|---|---|---|
| **预期设计** | 文档/契约有明确语义，agent-facing 描述与实现一致，且测试/注释确认 | 不违背任何已声明不变量；失败属于“策略质量”而非“完整性” | CM-04 的自由进化面；CM-03 的 soft budget 意图 |
| **未考虑的设计漏洞** | 两处契约冲突、或某语义从未定义；各自局部自洽但组合矛盾 | docs/primitive 表内部矛盾；测试只覆盖部分分支；“保守压缩”这类模糊措辞 | CM-05 的 note 压缩歧义；CM-03 的“预算 vs 时限” |
| **代码实现漏洞** | 文档已明确，实现遗漏/写错 | 兄弟 primitive 已有检查而此路径没有；agent-facing 承诺被违反；测试注释明确 | CM-05 的 `substitute`；CM-04 的 unknown face 默认；CM-06 的 saved 口径 |

**使用原则**：先问“文档是否说清”；说清了但代码没做 = 实现漏洞；文档自身矛盾/未说 = 设计漏洞；两者都成立时写“主/次”而不是二选一。

### 1.5.2 D 的三类行为（威胁模型）

| 类别 | 定义 | 判据 |
|---|---|---|
| **可接受自由进化面** | 文档明确鼓励、且不破坏 canonical/审计/权限的 agent CM 行为 | 内容仍来自 canonical 块或其机械派生；发送历史可被 audit 重建；写面仍走正常通道 |
| **被设计显式假设并声称挡住的恶意行为** | docs/10 P3 治理包（AST + `gan.*` 禁令 + “可达面 = CMSession + stdlib”）声称已挡住的行为 | 需要**故意规避**（伪造返回、`_s`、`sys.modules`、`gc`、`fork`、写文件、broker 伪造）；且 docs 明确说“够不到” |
| **正常情况下的真实漏洞** | 不需要恶意、也不属于“刻意边界”；遵守表面契约的代码或普通 bug 即可触发 | 不依赖隐藏知识；由正常扩展/拼写/策略循环/可移植性触发；docs 的承诺会被打破 |

**关键说明**：repo 的信任模型是**混合的**——
- docs/10 P3 明确声明“无沙箱，包容靠能力不可达”，所以上表第二类**在声明的威胁模型内**，挡住失败就是真实缺口，不能归为“恶意行为不在范围”；
- 但如果维护者改为“agent 可信、OS sandbox 是唯一边界”，则第二类降级为“文档化残余”，第一类/第三类仍须修：**正常路径的完整性漏洞不会因信任模型改变而消失**。

### 1.5.3 B：独立问题 vs A 的下游表现

判据：
1. 是否走**不同的进程/传输路径**（task child 不走 `RoleProcess`/`role_state`）；
2. 修 A 是否能修 B（不能，则独立）；
3. 是否有独立的 build/emit/ingest 证据链；
4. 失败侧（build 失败 / emit 失败）是否都只在 task 侧出现。

### 1.5.4 A：接线 / 功能未实现 / 实现错误

判据：
1. 核心 CM 在进程内是否有可运行证据（测试 + fix3 前真实轮）；
2. 子进程是否具备自建 session 的输入（design、projection、named 模块）；
3. 轨迹文件是否在子进程命名空间（决定 `traj_seg`/slice 是“接线”还是“未实现”）；
4. 现有 seat 分支是否消费 `cm_mode`/`fetch`/`offset`（决定是否已有实现错误）。

### 1.5.5 C：soft budget vs hard limit

判据：
1. 键名/consumer/文档是否承诺“终止”（`exec_ms`、overruns count toward wedge）；
2. 实现是否真的能终止（线程 wait / 进程 kill）；
3. 是否有独立的外部兜底（task `question_timeout_s` vs role 无）；
4. 进程内 signal/trace 是否可被被限制代码关闭（若是，则不是安全边界）。

## 2. 问题详情

### CM-01（P0）角色席位 CM 整体休眠

**问题简述**

在 driver 模式（当前唯一生产模式）下，planner/evaluator/self_improve 三个角色席位：
- `ctx_index` / `ctx_fetch` / `ctx_pin` / `ctx_view` 注册着但只会返回 `no context-management session is active`；
- `cost.cm_mode` 是死旋钮；
- `cm_assembly` / `cm_policy` / `METHODS` 永不执行；
- `session_token_budget` / `plan_token_budget` / `evaluate_token_budget` 也没有实际消费者；
- `read_trajectory` 的 slice/index 前端对角色不可达，seat 分支直接返回整块 blob；
- `cost_sessions.jsonl` 的 `cm` 字段恒为 null，但 `cost_keys_applied` 仍把这些键记为“in force”。

docs/17 §14.4 已登记；本审计确认在 HEAD `898d583` **仍然成立**。

**原因**

不是核心功能未实现，而是**席位边界缺少会话装配**：

1. `RoleProcess._invoke` 的 `role_state` 只携带 `attempt_id` / `tool_timeout_s`；
2. 子进程按**精确键集**接收并只回填这两个字段；
3. `loop` 把 `session_token_budget`、`session_cm_mode`、`cm_session` 盖在 **RoleProcess 代理对象**上（根进程）；
4. 根进程构建的 `cm_session` 和 `_materialize_traj` 结果对子进程不可见（对象不能跨进程序列化）；
5. 子进程没有自己的 `_build_cm_session`；
6. 因此 `BaseRole.run` 的 `cm` 参数始终为 None（除非显式传参，而 loop 的 plan/evaluate 调用不传）。

此外还有两层“部分实现”：

- **history 级 CM 可救**：子进程能读到自己的 design 配置（plan/evaluate 是 read-only bind；self 是可写 `ckpt/design/<role>`），且 `gan/framework` 与 `gan/components/<role>` 在只读投影里，理论上可以在子进程内自建 session（无需跨进程对象）。
- **轨迹面未实现**：子进程的 `output_dir` 是 `--tmpfs`，只挂载自己的 workspace / 本席位 trajectory 写根 / design 配置；**任务代际轨迹和前一 outer 的 session 文件不在命名空间**。所以 `traj_seg`/`ctx_index` 轨迹段/`read_trajectory` slice 必须走 broker RPC 或根侧载荷，docs/17 §15.1/§17.6 的方案二/三明确 defer。

**判断（A）：边界装配缺失 + 部分功能未实现 + 若干实现错误；不是核心功能未实现，也不是核心逻辑错误。**

判据：

- **核心功能可用**：`test_cm.py` 245/245、`test_cm_integration.py` 32/32；fix3 前真实轮 `pr_o1i1_cm_145651` / `pr_o1i1_postfix2` 有 34/33 条 `cm_view` 和含 `cm` 的 cost 行 → CM 原语、assembly、fail-open、audit 在进程内是成立的；
- **装配缺失**：子进程没有 `_build_cm_session`，`role_state` 不携带 cm 键；但子进程能读 design（plan/evaluate 只读 bind；self 可写）并从只读投影解析 `gan/components/<role>/cm`，所以 **history 级 CM（slice/compact、ctx_note/ctx_budget、named assembly/policy）属于“装配 + 小型新代码”，不是功能未实现**；
- **轨迹面未实现**：`output_dir` 在子进程是 `--tmpfs`，只挂载 seat 自己的 trajectory 写根与 design；**任务代际轨迹 / 前 outer session 文件不可见**，`traj_seg`/`ctx_index` 轨迹段/`read_trajectory` slice 必须有 RPC/载荷协议 → 这是**功能未实现**，不是接线；
- **实现错误（复活后会显形）**：`_resolve_cm_module` 用 `outer_<O>` 而非 `outer_<O>__<seat>`；`read_trajectory` seat 分支不消费 `session_cm_mode`/`fetch`/`offset`；`_record_session_cost` 用根侧 summary（turns=0）；`cost_keys_applied` 在无消费者时仍声称 in force。

**只改 `role_state` 能救回什么、救不回什么**：

- 能救回：`session_token_budget`、`session_cm_mode`（pure wiring）；child-side factory 后 history slice/compact、ctx_note/ctx_budget、named module 执行；
- 救不回：`ctx_index` 的 `traj_seg` 面、`read_trajectory` slice/fetch/offset —— 这些必须补协议，不能只把属性传过去。

**问题轨迹分析**

```
design cost.cm_mode / cm_assembly
  → loop._effective_cost_keys()  (根进程)
  → loop._build_cm_session() + _materialize_traj()  (根进程，构建了但用不到)
  → self.planner.session_cm_mode = ...
  → RoleProcess proxy (属性只在根进程)
  → _invoke 只发 role_state={attempt_id,tool_timeout_s}
  → 子进程 role 无 cm_session / 无 session_cm_mode / 无 token_budget
  → chat_with_agent(cm=None)  → 无 seam
  → ctx_* = NO_SESSION；read_trajectory seat 分支 = 整块 blob
  → cost_sessions cm=null；cost_keys_applied 仍声称 in force
```

- p/e 永远得不到 slice/compact；上下文成本控制对角色完全失效；
- ctx 工具是“注册着但永远报错”的死工具（docs/17 已观察到 evaluator 调用 `ctx_index` 得到 no session）；

**解决方向（不是“只接线”）**

1. **纯接线**：`session_token_budget` / `session_cm_mode` 进 `role_state` 或 role 方法参数；

### CM-02（P0/P1）task 侧 CM 审计 sidecar 空转（独立于 CM-01）

**问题简述**

真实 driver 轮中，task 侧每个 generation 都出现 `cm_events_ingest_empty`，`runs/<genid>/cost.json` 的 `task_cm` 为 `{"absent": true}`，`cm_session_degraded` 也为 0；task 侧 CM 的事件/降级证据完全丢失。

**原因**

**这是独立问题，不是 CM-01 的下游表现。** task child 不经过 `RoleProcess` 的 `role_state` 传输，而是：
`domains/harness` → `domains/task_worker` → `TaskAgent` → `chat_with_agent`，自身有 `_build_cm_session`。

证据链指向**审计 sink 的属主/权限**：

1. `assemble_task_env` 在 outer worker（`ganop`）中 `open(...,"a").close()` 创建 `run_dir/cm_events.jsonl`；
2. driver 使用私有 umask `0o077`，实际文件是 `ganop:0600`；
3. task child 经 `setpriv` 降权到 `rsi_gan_task`；
4. bwrap 的 `--bind` 不改变属主/mode，`/workspace/cm_events.jsonl` 仍是 `ganop:0600`；
5. child 的 `_cm_emit` `open(...,"a")` → `EACCES`；
6. fallback 写 `os.getcwd()/cm_events_failed.jsonl`，而 child 的 cwd 是 `/workspace/scratch`（`--tmpfs`），随沙箱销毁；
7. host sidecar 保持 0 字节；`task_runner._ingest_cm_events` 只能发 `cm_events_ingest_empty`；
8. 失败侧的 `cm_session_degraded` 也走同一 sink，因此同样丢失。

```
design cost.cm_mode=slice

  → TaskAgent(cm=...) → chat_with_agent(cm=...)  (seam 运行)
  → cm.emit = _cm_emit
  → open("/workspace/cm_events.jsonl","a")  ← ganop:0600，child uid=EACCES
  → fallback → /workspace/scratch/cm_events_failed.jsonl  ← tmpfs，随沙箱销毁
  → host sidecar 0 bytes
  → task_runner: cm_events_ingest_empty("sidecar present but no seam events")
  → cost.json task_cm = {"absent": true}
```

证据：

- 保留 work 树中 `work/0/repo/cm_events.jsonl`：`-rw------- ganop ganop 0 bytes`（`small_1029_231632`、`smoke_1022_213938`）；
- 最新完整轮 `small_1031_110220`：`cm_events_ingest_empty` ×4，`cm_session_degraded` = 0，`task_toolset_assembled` 的 `cm.core_files` 9 个 sha 与 HEAD 一致；

**待区分的一个子情形**

现有证据不能 100% 区分：
- **(a) session 构建成功，但 emit 写不进**（权限；最可能）；
- **(b) session 构建失败，`_degrade` 的 `_cm_emit` 也写不进**（同样表现为空）。

以 child uid 尝试 append 该 sidecar、或把 sidecar 改为 child uid + `0660` 后再跑一题；事件出现即确认 (a)。

**判断（B）：独立问题，不是 CM-01 的下游表现。**

判据：

1. **路径独立**：task child 不经过 `RoleProcess`/`role_state`；它走 `domains/harness` → `domains/task_worker` → `TaskAgent`，自身有 `_build_cm_session`；

3. **修 B 不修 A**：把 sidecar 改成 child uid 可写，p/e 席位仍没有 `cm_view`；

5. **两种子情形仍在 task 侧**：即使真实原因是 build 失败，其 `_degrade` 也走同一不可写 sink，仍与 CM-01 无关。

**待确认**：本节不把 (a)/(b) 写成定论；需 §6 的 child-uid append 探针或 sidecar 属主修复后重跑一题才能区分。

### CM-03（P1）`cm_*_exec_ms` 不能按时终止，且无其他兜底

**问题简述**

`cm_policy_exec_ms` / `cm_assembly_exec_ms` 名义上是“执行预算”，实际不能终止超时代码；死循环会永久挂住角色会话。`cm_policy_overrun` / `cm_assembly_overrun` 事件几乎不可达；模块加载不在预算内。

**原因**

`run_policy` / `run_assembly` 使用：

```python
with concurrent.futures.ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(...)
    future.result(timeout=...)
```

- `future.cancel()` 对**正在运行**的线程无效；
- `with` 退出执行 `shutdown(wait=True)`，即使 `result` 已超时，仍会等线程跑完才抛异常；
- 因此“超时”只是延迟抛出，不是终止；
- 死循环永远不会返回 → `_POLICY_STRIKES` 不增加 → 2 击熔断失效；
- `load_policy`（每轮）和 `load_assembly`（一次）在 executor **之前**执行，模块级死循环完全绕过预算；
- 角色侧没有父级 wall timeout：`RoleProcess._invoke`/`_read_message` 无超时；task 侧只有 `question_timeout_s`（300/1200s）这个粗粒度外部 kill。

**设计意图与预期作用（C）**

`cm_policy_exec_ms` / `cm_assembly_exec_ms` 不是单纯“限时数字”，其设计意图由 docs/10 §10/§11 与 `cost_keys` 的 consumer 描述共同构成：

1. **限制每轮 agent CM 代码的额外延迟**：policy 只挂在 `custom` 档尾部，assembly 替换整条 pipeline，成本形态不同，所以两个键分立；默认 200ms 是“每轮可接受的编排开销”量级。
2. **给 2 击 wedge breaker 提供失败来源**：超时/崩溃/契约违约都算一次失败；2 次后 `cm_policy_disabled` / `cm_assembly_disabled`，回落到 fixed pre-segment / 基线 preset，保证会话不被 agent CM 代码炸掉。
3. **fail-open + 可观测**：`cm_policy_failed` / `cm_assembly_failed`（带 `struck`）、`cm_view.stats.degraded`、熔断后每轮 `assembly_disabled`、ledger `cm_assembly_failures`、receipt `budget.kind=cm`。
4. **可演化的运行参数**：保留 cost 键、clamp 到 `[10, 10000]`，agent 可按自身 policy/assembly 复杂度调参。

**判断（C）：设计意图是“soft budget + 熔断 + fail-open + 可观测”，不是安全边界；当前实现连 soft budget 也没有真正达成。**

判据：

- **文档语义 vs 实现**：consumer 写 “overruns count toward the wedge breaker”，但 `ThreadPoolExecutor` + `with shutdown(wait=True)` 使超时变成“晚到异常”，不是终止；
- **实测**：100ms 预算 + 500ms 函数 → `0.504s` / `0.515s` 才抛异常；`while True` 永不返回 → 不计击、不熔断；
- **overrun 事件**：能正常返回时 `over_ms` 通常为 0，`cm_policy_overrun` / `cm_assembly_overrun` 几乎不可达；
- **load 不在预算**：`load_policy`（每轮）、`load_assembly`（一次）在 executor 之前，顶层死循环绕过一切预算；
- **没有外部兜底**：角色侧无 `RoleProcess` wall timeout；task 侧只有 `question_timeout_s`（粗粒度整题 kill）；
- **不是安全边界**：进程内 `signal`/`settrace` 可被被限制代码关闭/逃逸（`import signal`、threading、`os.fork`）——**真正的硬限需要进程隔离 + 父侧 kill**。

**结论**：应改成真实时限，或诚实地降级为 advisory；不能继续让 `exec_ms` 以“硬时限”的口吻存在。

**问题轨迹分析**

```
policy apply() / assembly assemble()
  → ThreadPoolExecutor.submit
  → future.result(timeout=200ms)
  → TimeoutError
  → future.cancel() 失败（running）
  → with 退出 shutdown(wait=True)
  → 等待线程实际结束（死循环 = 永久）
  → 无 cm_policy_failed / 无 strike / 无 cm_view
  → 角色会话/outer 永久挂起
```

实测：

| 场景 | 结果 |
|---|---|
| 100ms 预算 + 500ms assembly | `AssemblyTimeout`，`elapsed=0.504s` |
| 100ms 预算 + 500ms policy | `PolicyTimeout`，`elapsed=0.515s` |
| 100ms 预算 + 模块顶层 `sleep(0.3)` | 实际 `elapsed=0.325s`（load 未计预算） |
| `while True` policy | 永不返回；无 strike / 无事件 |

**代码定位**

- `gan/framework/cm/assembly.py:367-390`（`run_assembly`；`with` 在 378）
- `gan/framework/cm/failopen.py:93-115`（`run_policy`；`with` 在 109）
- `gan/framework/cm/failopen.py:64-75`（`load_policy` 在 executor 之前）
- `gan/framework/cm/session.py:790-...`（`run_policy`）
- `gan/framework/cm/session.py:577-620`（`_load_named`：load 无预算）
- `gan/framework/role_process.py:457-...`（`_invoke` 读消息无超时）
- `gan/framework/loop.py` plan/evaluate/self_improve 调用处（无 wall timeout）
- `gan/framework/cost_keys.py:131-140`（键的 consumer 声明）
- `docs/10_成本反馈闭环设计.md:1173-1178`（P2 的“每轮 worker 线程 + 预算”描述）

**影响**

- agent-authored CM 代码可把整个 outer 挂死；角色侧没有 `question_timeout_s` 兜底；
- `cm_policy_overrun` / `cm_assembly_overrun` 形同死事件；
- 2 击熔断只能处理“会返回的慢代码/异常”，不能处理死循环；
- `cm_policy_exec_ms` 的文档语义（超时计击、熔断）与实现不一致。

**解决方向**

1. **最低成本**：给 `RoleProcess`/loop 的角色调用加父侧 wall timeout（kill/restart worker，走 `planner_failed`/`evaluator_failed`）；这是现在完全没有的兜底；
2. **若要保持“硬执行边界”**：把 policy/assembly 放到可 kill 的子进程/worker；进程内 `signal.setitimer` / `sys.settrace` 可作临时缓解，但不是安全边界（被限制的代码可 `import signal` 关 timer、`threading`/`os.fork` 逃逸）；
3. **把 `load_policy` / `load_assembly` 纳入同一个计时/进程边界**；
4. **若暂时不进程隔离**：把键改名为 soft / advisory，超时后不要 `shutdown(wait=True)` 等待；`overrun` 改为“返回后测量 elapsed”并 emit；
5. 默认值校准：200ms 对“软阈值”合理，对“真 kill”偏激进（建议 1s 左右或分档）。

**验收**

- `while True` policy/assembly 在预算内被终止，产生 `cm_policy_timeout` / `cm_assembly_timeout`（或既有失败事件）+ strike + 后续 `cm_view.degraded`；
- 无残留线程/进程；角色会话超时后 outer 能按失败路径收敛；
- `load_policy` 的模块级死循环同样被终止；
- 守卫测试证明 `future.cancel()` 对运行中线程无效（防止误以为已修）。

### CM-04（P1）具名 assembly/policy 的信任边界名不副实

**问题简述**

代码注释/文档声称“assembly 可以重排/扩展阶段，但不能绕过规则”“no-fabrication by construction”“agent CM 代码可达面 = CMSession + stdlib”。实际实现中，具名 assembly/policy 可以在多个层面绕过这些声明。

**原因**

1. **assembly 返回值只做形状校验**：`(list, str)`，不校验长度/条目/来源；可返回伪造的 history/outgoing；
2. **直接对象访问**：assembly 可改 `msgs` 原列表（canonical history）、直接操作 `session.universe`/`session.view`；`ViewHandle` 暴露 `_s`（`test_cm.py:182` 自身承认 `ctx._s.notes.clear()` 静态不可检测）；
3. **未知 face 默认升级**：`_faces_for(face)` 对任何非 `"agent"` 返回 `POLICY_FACES`；`_budget` 只在 `face == "policy"` 时设置；`ViewHandle(session,"not-a-face")` 可 `compact`/`substitute` 且无 ops 预算；
4. **policy 写 note**：`ViewHandle.note_write` 在 policy face 也可用，与“policy 只读+保守压缩”相反；
5. **AST 负面清单不是能力边界**：只禁少量 import/call；`os` / `importlib` / `pathlib` / `shutil` / `threading` 都可用；`os.remove`、`Path.write_text`、`importlib.import_module("socket")`、`os.fork` 不触发；
6. **双姿态 gate 可绕过**：`_gan_import_problems` 对 `try ... except ImportError` 内的**任何** `gan.*` 导入放行，不限于 `cm`；`load_policy` 根本不跑 `_gan_import_problems`（只有 assembly 跑）；preflight 的 `cm_component_problems` 只是 advisory；
7. **`sys.modules` / `gc`**：即使 import 语句被禁，已加载的 `gan.*` 模块仍可通过 `sys.modules` 触达；`gc.get_objects()` 可找到 session/broker 等对象。

**问题轨迹分析**

- **假 assembly**：返回值 `([fake history], "fake outgoing")` → 被 `assemble_turn` 原样接受；`summary()` 显示 `assembly_active=True`、`blocks=0`，审计没有内容证据。
- **face 逃逸**：`ViewHandle(session,"not-a-face").compact([...])` 返回 `ok=True`，对 pinned 块 `substitute` 返回 `ok=True`；`_budget=None`。
- **policy note 注入**：`ViewHandle(session,"policy").note_write("policy-injected note")` 返回 `ok=True`，universe 多出一个 `note` 块。
- **guarded gan import**：`try: from gan.framework import code_repo` 拼接后 `_gan_import_problems` 返回 `[]`，`load_assembly` 成功。
- **policy 的 gan import**：`from gan.framework import code_repo` 经 `policy_violations` 返回 `[]`（`load_policy` 不跑双姿态 gate）。

**代码定位**

- `gan/framework/cm/session.py:555-560`（assembly 返回值校验）
- `gan/framework/cm/session.py:926-...`（render：直接对象状态是视图来源）
- `gan/framework/cm/session.py:110-120`（`_budget` 仅 exact "policy"）
- `gan/framework/cm/session.py:204-217`（`note_write`）
- `gan/framework/cm/ops.py:37-41`（`_faces_for` 默认 policy）
- `gan/framework/cm/assembly.py:304-340`（`_gan_import_problems` / guarded import）
- `gan/framework/cm/failopen.py:27-61`（`policy_violations` 负面清单）
- `gan/framework/cm/failopen.py:64-75`（`load_policy` 无 `_gan_import_problems`）
- `gan/framework/preflight.py:393-445`（`cm_component_problems` advisory）
- `scripts/local/test_cm.py:182`（`ctx._s` 逃逸被承认）

**影响**

- “assembly 不能绕过规则”的信任声明失效；
- 审计面（`cm_view`/summary）不能证明 agent CM 代码做了什么；
- 若未来把 role CM 复活（CM-01），这些代码在角色进程内可触达 broker/审计写入口（OS 沙箱仍限制文件写，但审计伪造/越权面存在）；
- AST gate 被误当作安全边界（实际只是纵深防御）。

**影响分层（D）**

| 影响层 | 具体后果 |
|---|---|
| 上下文完整性 | assembly 可返回伪造 history/outgoing，或直接改 canonical `msgs`；`render` 的 no-fabrication 约束被绕过 |
| 审计/可复现性 | 具名 assembly 的 `cm_view` 只有合成最小视图（ops 为空）；直接操作 `session/universe/view` 不产生 ops/violations；“双记”无法回答“这一轮到底发送了什么” |
| 权限/写面 | unknown face 拿 policy 能力；`_s` 暴露 session；policy 可写 note；role 子进程 CM 代码可写自己的 workspace/logs/trajectory，self 席位可写 `ckpt/design/<role>`；`broker.log_event` 可伪造审计事件（`_dispatch_broker` 的 identity 检查刻意排除 `log_event`） |
| 演化质量 | “裁太多/策略差”是策略质量，属自由进化面；但伪造 canonical/伪造审计/直写 design 是完整性失守，不是质量 |
| 可用性 | 死循环/线程/信号逃逸；主要与 CM-03 重叠，D 不是主要来源 |

**关键校准**：OS sandbox（bwrap + setpriv + uid）仍限制文件/进程越界；`_dispatch_broker` 也限制 role/node/seat。所以 D 不是“直接拿到 repo root/其他席位”的 shell 逃逸；它主要是**席位内部的能力越权、审计伪造、写面绕过**。但在 self 席位，`ckpt/design/<role>` 本来就是可写根，CM 代码绕过 `save_self_config`/design heal 直接写 JSON，是实际写路径缺口。

**判断与三类划分（D）**

**验收**

- `ViewHandle(session,"not-a-face")` 被拒绝或只得到 agent face；
- pinned/note 在 policy face 不可变（见 CM-05）；
- 假 assembly 返回被拒绝（`AssemblyError`）并触发 fallback；
- policy 的 `from gan.framework import code_repo` 被 load gate 拒绝；
- `sys.modules`/`gc` 逃逸在文档中明确列为已知残余，不宣称“可达面只有 CMSession”。

### CM-05（P1）pinned / note 不变量可被 `substitute` 打破

**问题简述**

`drop` 与 `compact` 都拒绝 pinned / note，但 `substitute` 只在 `form == "placeholder"` 时拒绝 pinned；对 `head_tail` / `excerpt` / `template` 既不检查 pinned，也不检查 `kind == "note"`。因此 policy 可以压缩 pinned 指令/笔记，违反“pinned blocks survive every compaction”“note blocks are never dropped”的声明。

**原因**

`ops.substitute` 的校验条件不完整（只覆盖 placeholder 形式）。

**问题轨迹分析**

```
policy: handle.substitute(pinned_block, "excerpt")
  → ops.substitute:
      form != placeholder → 跳过 pinned 检查
      chars >= floor → 跳过 floor
      view.set(form=excerpt)
  → 下一次 render: cut(block.text, EXCERPT_KEEP) 替换原内容
  → pinned 指令/note 被压缩，仍报告 ok=True
```

实测：
- pinned note 2000 字符 → `substitute(excerpt)` `ok=True`；
- pinned turn_output 2000 字符 → `substitute(head_tail)` `ok=True`。

**功能框架与预期作用（E）**

CM 的视图模型是 `Universe`（add-only 块）+ `View`（每块形态 `full/head_tail/excerpt/placeholder/template/dedup/derived_host`）；`render` 按形态把块渲染进发送历史，`cut(...)` 保留首尾并插入省略标记，placeholder 完全去内容，template 只留元数据。

四个会改变视图的操作：

| 操作 | 语义 | 是否内容损失 |
|---|---|---|
| `drop` | 整块变 placeholder（驱逐） | 是（全丢） |
| `compact` | 机械压缩（excerpt/first_last/merge/template） | 是 |
| `substitute` | 原位改形态（full ↔ head_tail/excerpt/placeholder/template） | 是（非 full 都丢内容） |
| `fetch` | 恢复 full | 否（恢复） |

`pin` / `note` 的设计作用：

- `pin`：agent 通过 `ctx_pin` 申请“这块必须保留”，policy 必须尊重；`ctx_pin` 的 agent 描述写的是 “pinned blocks survive **every compaction**”；
- `note`：`ctx_note` 写入的块**自动 pinned**，agent 描述是 “auto-pinned; never dropped by assembly”；policy 面被设计为“只读 + 保守压缩”。

`test_cm.py:637` 的注释把预期说得更直白：

> `pin = never dropped/compacted; the dedup prefix-elision is the one deliberate exemption (it keeps the body, drops only the repeated header)`

也就是说，预期的 pin 是**对所有 compaction 形态都保护**，只有 `dedup`（只删重复 header、保留 body）是刻意豁免；`substitute` 到 head_tail/excerpt/template 都丢内容，属于 compaction 语义，不在豁免内。

**判断（E）：主 = 代码实现漏洞；次 = 未考虑的设计缺口；不是预期设计。**

判据：

1. **代码实现漏洞（主）**：
   - `drop`、`compact` 都成对实现了 pinned + note 检查；`substitute` 也写了 pinned 检查，但**只覆盖 placeholder**（`ops.py:80-82`）——更像作者认为“只有 placeholder 才算 drop”，忘了 head_tail/excerpt/template 也丢内容；
   - `ctx_pin`/`ctx_note` 的 agent 描述、`test_cm.py:637` 的注释都指向“所有 compaction 都受保护”；若 `substitute` 是预期豁免，这些描述和测试需要同步改，仓库没有记录；
   - `test_cm.py` 只测了 window/compact 的 pinned 保护，没有测 substitute —— **测试覆盖缺口**，不是“设计上允许”。
2. **未考虑的设计缺口（次）**：
   - docs/10 note 行写 “policy 只读 + **保守压缩**”，可解读为“policy 可对 note 做保守 excerpt”；但同处又写 “永不丢 note 块”，`ops.compact` 也拒绝 note，`ctx_note` 描述说 “never dropped”；**“保守压缩”到底允不允许 note 被 excerpt，设计未裁决**；
   - `pin` 对 `substitute` 的语义未在 primitive 表写明（“原位改形态”是否受 pin 约束）——契约未定义，需要补一条裁定。
3. **不是预期设计**：若把 `substitute` 视为 pin 的合法豁免，会让 `ctx_pin` 的“框架保证尊重”和 `ctx_note` 的“never dropped”变成假话；且 `dedup` 已被明确认定为“唯一刻意豁免”，没有第二个豁免的文档依据。

**影响（按正常路径排序）**：

- **pinned 首条 instruction（最严重）**：custom policy / 具名 assembly 用 `substitute(excerpt/head_tail)` 就能压缩首条 user instruction；`ctx_index` 不显示 form（CM-06），只有 `ctx_view` 能看到；
- **pinned 历史 turn**：策略若做“压缩所有大块”的循环，容易顺手把 pinned 块也 excerpt；这不是恶意，是正常“策略写得太粗”；
- **note**：`msg_index=None`，`render` 跳过，所以实际发送内容不受影响；但 view/审计/`est_chars_saved` 被改写，`ctx_note` 读到的全文仍来自 `session.notes`，造成“内容还在、视图说没了”的审计不一致；
- **审计**：返回 `ok=True`，不产生 `cm_violation`。

**代码定位**

- `gan/framework/cm/ops.py:71-95`（`substitute`；pinned 只在 80-82 检查 placeholder；note 无检查）
- `gan/framework/cm/ops.py:62`（`drop` 的 floor）
- `gan/framework/cm/ops.py:137`（`compact` 的 floor/pinned）
- `gan/framework/cm/session.py:730-790`（`window_defaults` / `conservative_compaction` 只跳过 pinned，不代表 policy 面也受约束）

**影响（补充：审计与契约）**

- agent 的 pin 申请（`ctx_pin`）可被 policy 绕过；框架对 pin 的保证不成立；
- note 内容在视图/统计层可被改写（实际发送因 `msg_index=None` 不受影响）；
- 审计仍记为 `ok=True`，不产生 violation。

**解决方向**

- `substitute` 对所有 pinned / note 统一拒绝除 `full` 之外的 form；
- 或把 pinned/note 保护集中到一个 `_validate_mutable(block, form, floor)`，所有原语共用；
- 新增守卫：pinned/note 的 drop/compact/substitute 全矩阵拒绝。

**验收**

- policy face 对 pinned/note 的 `head_tail/excerpt/template/placeholder` 全部 `ok=False`；
- agent `ctx_pin` 后的块在整个 session 中内容不变。

### CM-06（P2）审计/统计/agent face 描述漂移

**问题简述**

若干 agent 可见的“知情权”面与内部统计口径和代码不一致，存在静默截断与误导性描述。

**原因与定位**

1. **`ctx_index` cap 200 静默截断**
   - `gan/framework/cm/ops.py:258-262`：`universe.ordered(kinds)[:cap]`，无 hidden count / marker；
   - 260 块实测只返回 200（`len=200`），agent 看不出还有 60 个。
2. **`peek` cap 16k 无标记**
   - `gan/framework/cm/ops.py:249-255`：`block.text[:cap]`，`chars` 是真实值；40000 字符实测只返回 16000，无“已截断”标记。

4. **`template` saved=0**
   - `gan/framework/cm/ops.py:92`：只有 excerpt/head_tail 计 saved；template 替换为元数据但报告 0。
5. **`traj_seg` 的 saved 虚高**
   - `session.py:926-936` 的 `render` 对 `msg_index is None` 的块直接跳过；
   - `traj_seg` 是 `msg_index=None`，policy 对它 `substitute/drop` 会计入 `est_chars_saved`，但它从未进过上下文。
6. **`ctx_view` 描述有 stats，实际没有**
   - `faces.py:120` 写 “per-turn assembly stats”；
   - `ops.view_state`（`ops.py` 末尾）只返回 `forms`，无 stats。
7. **`ctx_index` 描述说 derived “never produced”**
   - `faces.py:73` 仍写 “kb_note/boundary/derived ... never produced”；
   - 但 merge/template 已经物化 `derived`（docs/10 §15）。
8. **`ctx_budget` 描述说 reasoning split**
   - `faces.py:90` 写 “with reasoning split when available”；
   - `_cm_usage_reader` 只累计 `total_tokens`，无 reasoning 拆分。
9. **`ctx_pin` 描述说框架保证尊重**
   - `faces.py:100`；实际被 CM-05 打破。
10. **cost/receipt 的 cm 摘要**
   - `loop.py:732-800` 用根侧 session 的 `summary()`（turns=0）填 cost 行；`if cm_sum.get("turns")` 导致 `cm` 恒 null；
   - 但 receipt `budget.cm` 仍可能带 `mode/turns:0`（`loop.py:2559-2560`），与 cost 行不一致。
11. **`cm_traj_materialized` 对未使用 session 发事件**
   - `_materialize_traj` 在根侧执行（`loop.py:1105-1120`），若 cm_mode 非 passthrough，会 emit `cm_traj_materialized`，但该 session 从不会被使用。

**影响**

- agent 依据 `ctx_index` 以为看到了全部块，实际不是；
- policy 依赖 `peek` 拿到部分内容却以为是全量；
- `est_chars_saved` 与 `cm_view` 的统计口径不可对账；
- agent-facing 描述与实现不一致，属文档/契约漂移。

**解决方向**

- `index_blocks` 返回 `total` / `hidden` / `capped`，并在 `ctx_index` 描述中说明；
- `peek` 加 `truncated` / `shown_chars`；
- `substitute` 的 saved 用实际 form 的 `keep`；template 用实际替换长度；
- `render` 只把真正进入历史（`msg_index != None`）的 block 计入视图节省（或明确 traj 为“可 fetch 材料”，不计 saved）；
- `view_state` 补 stats，或改 `ctx_view` 描述；
- 更新 `faces.py` 的 derived/reasoning/pin 文案；
- cost/receipt 统一从子进程/任务侧 summary 取数（与 CM-01/CM-02 一并修）。

**验收**

- 260 块时 `ctx_index` 明确显示 `hidden=60`；
- `ctx_view` 返回 `forms + stats` 或描述改为仅 forms；
- `est_chars_saved` 与逐块 form 计算一致；
- `ctx_pin` 的“尊重”在 CM-05 修复后成立。

### CM-07（P2）workspace-first 解析路径错误 + 模块名未消毒 + policy 热加载

**问题简述**

1. `_resolve_cm_module` 用 `workspaces/<role>/outer_<O>/src`，但角色真实工作区是 `workspaces/<role>/outer_<O>__<seat>`；workspace-first 实际永远看不到活跃工作区，还会创建游离目录；
2. `cm_policy` / `cm_assembly` 的 `stem` 未做 basename/越界校验，`../` 可穿越出 `cm/`；
3. policy 每轮重新 `load_policy`，与“load-once per session”的 assembly 语义不对称；self_improve 若在同一会话内改 policy 文件，下一轮会热加载新代码。

- `AccessBroker.src_dir(role,node_id)` 是通用 `workspaces/<role>/<node_id>/src`；role 子进程的 `_dispatch_broker` 会把 node_id 重写为 `outer_<O>__<seat>`（`role_broker.py:767`），但根侧 loop 直接调用 `src_dir` 时没有 seat 后缀；

- `run_policy` 每次 `load_policy`（`session.py:790` → `failopen.py:103`），而 `_load_named` 只加载一次并缓存。

**问题轨迹分析**

```
loop._resolve_cm_module(role, stem, outer)
  → broker.src_dir(role, "outer_3")          ← 错误键（应为 outer_3__plan）
  → workspaces/role/outer_3/src/...          ← 活跃工作区是 outer_3__plan/src
  → 文件不存在 → 回落 committed tree
  → 若 stem 含 "../" → 可解析到 cm/ 之外
```

**代码定位**

- `gan/framework/loop.py:969-999`（`_resolve_cm_module`；986 的 workspace key）
- `gan/framework/access.py:131-140`（`workspace`/`src_dir` 的通用键）
- `gan/framework/role_broker.py:767`（真实 writable workspace `instance__seat`）
- `gan/framework/role_process.py:632-649`（`_dispatch_broker` 的 seat_node 重写）
- `gan/framework/task_execution.py:419-431`（`_deliver` 的路径拼接，无 basename 校验）
- `gan/framework/cm/session.py:790`（`run_policy`）
- `gan/framework/cm/failopen.py:103`（`load_policy` 每轮）
- `gan/framework/cm/session.py:577-620`（`_load_named` 缓存）

**影响**

- workspace-first 名存实亡（当前因 session 不用而没暴露；CM-01 修复后会立即显形）；
- 路径穿越是潜在读写面（当前 root-side 解析、未执行；复活后风险上升）；
- policy 的会话内热加载与 assembly 的“无热加载”策略不一致，可能被 self_edit 用来改自身 seam。

**解决方向**

- `_resolve_cm_module` 接受 `seat`，使用真实 `outer_<O>__<seat>`（或直接通过 `broker` 的 seat 重写路径）；
- 对所有 design 传入的 stem 做 `os.path.basename` + 仅允许字母数字下划线 + 检查最终路径在 `gan/components/<role>/cm/` 内；
- 明确 policy 的 load-once 语义，或显式接受“policy 可热加载”并记录；
- 清理 `src_dir` 创建游离目录的副作用。

**验收**

- workspace-first 在真实 seat 下命中并加载 workspace 文件；
- `stem="../../evil"` 被拒绝；
- policy 在会话内编辑自身文件后行为不变（或按显式契约变化并审计）。

## 4. 修改优先级与问题细分（接入 → 可运行 → 单点功能 → 细节）

排序原则：

1. **先接上**：session/审计真正进入 driver 链路，否则后续修复无法在真实路径验证；
2. **再可运行**：修“会挂死 / 破坏 canonical / 伪造审计 / 绕过 self 写路径”的核心问题；
3. **再做单点**：逐工具、逐键补齐功能与口径；
4. **最后细节**：文档、测试矩阵、残余声明、命名/typo。

四层是“完成定义”的递进，不是四选一：L1 不承诺语义正确；L2 不承诺工具完整；L3 不承诺文档一致；L4 不承诺新功能。

## 8. 一句话总结

> CM 的**原语层**是可用的；当前的主要风险在**边界层**：
> 角色席位没有 session（CM-01），task 侧审计 sink 不可写（CM-02），执行预算不能终止（CM-03），
> 而具名 agent 代码的信任边界、pinned 不变量、审计口径和轨迹分页都存在实现缺口（CM-04..08）。
> 修复顺序应是 **L1 接线/会话装配 → L2 核心可运行 → L3 单工具/键 → L4 细节**（细分见 §4）；
> 其中 L1 的 history CM 可以 child-side 自建，但 traj_seg/slice 必须补 RPC 或载荷协议，不能只“把属性传过去”。

**判定汇总（本轮讨论）**

- **A（CM-01）**：不是核心功能未实现，也不是核心逻辑错误；是**边界装配缺失 + 轨迹面未实现 + 若干实现错误**。只改 `role_state` 能救回 token budget / cm_mode / history slice；救不回 `traj_seg`/`ctx_index`/seat slice。
- **B（CM-02）**：**独立问题**，不是 A 的下游；最可能是 task sidecar 的 `ganop:0600` + child uid + `/workspace/scratch` tmpfs 导致 emit 失败；需 child-uid append 探针确诊。
- **C（CM-03）**：设计意图是 **soft budget + 2 击熔断 + fail-open + 可观测**，不是安全边界；实现连 soft budget 都没达成（超时不终止、overrun 事件不可达、load 不在预算、role 无兜底）。
- **D（CM-04）**：信任模型混合；三类并存——**可接受自由进化面**（pipeline 重排/策略差/primitive 组合）、**被设计显式假设并声称挡住的恶意行为**（伪造返回、`_s`、`sys.modules`/`gc`、fork/写文件/broker 伪造）、**正常路径真实漏洞**（返回不校验、`msgs` 未复制、`_s`/note_write、缺双姿态 gate）。不能一概归为“恶意边界”。
- **E（CM-05）**：**主 = 代码实现漏洞**（`substitute` 漏 pinned/note 校验，pinned 只覆盖 placeholder）；**次 = 未考虑的设计缺口**（note“保守压缩”语义未定义、pin 对 substitute 未写清）；**不是预期设计**——现状会让 `ctx_pin`/`ctx_note` 的承诺失真。

  - ✅ 已实现，且正常路径可达（进程内直连和 task 子代代码路径都算“可达”，但有前提时在备注写明）；

  - 🧪 有测试覆盖，但测试只覆盖进程内/直连路径，不代表生产路径可用。
- **两个“正常路径”必须分开说**：
  - **进程内（in-process）**：plan/evaluate/self 在根进程直接调用 `BaseRole.run` 的旧路径，也是 `test_cm*.py` 覆盖的路径；
  - **driver**：fix3 之后角色在 `RoleProcess` 子进程运行的唯一生产路径。当前 CM 在 driver 角色席位整体休眠（CM-01），不能把进程内的“绿”当成 driver 的“可用”。

### 9.10 功能侧差距归纳（只列结论，不重复修复方案）

1. **接线缺口是“面”不是“点”**：不是只缺一个 `role_state` 字段；child 侧还要有 factory、named 解析、轨迹物化、emit 落盘、cost 回传，缺一不可（F1.6/F1.7/F1.12-F1.15）。
2. **原语层的“主体”是完整的**：block/universe/view/render/三档 pipeline 都能跑；真正的洞集中在“保护性原语”（substitute）、“预算/失败语义”（exec）与“边界信任”（assembly 返回、`_s`、`msgs`）。
3. **task 侧不是“没实现”，是“实现了但审计通道不成立”**：代码路径、env、snapshot、ingest 都在；sidecar 属主/权限使事件写不进去（CM-02）。
4. **单工具/单键的缺口多为“口径不诚实”**：index/peek 的 cap、saved 的 600、cost 摘要字段、face 描述、read_trajectory 的 seat 分支；不改变主 pipeline，但会让 agent/审计读错事实。
5. **文档面已超前**：seeds、AGENTS、docs10 §11.6 的“角色侧正常”是 fix3 前 in-process 的事实，不能直接用于 driver 现状。

| `broker_info` | 跨进程 JSON | 9 键，含 ablation 标志；不含 CM 键 |
| `_validated_result` | 跨进程校验 | 角色方法返回字段集必须精确匹配，新增 CM 字段会被拒 |
| `GAN_CM_CORE/POLICY/ASSEMBLY/EVENTS` | 子进程 env | task 子代的快照入口/具名模块/审计路径 |
| `cost` 记录里的 `cm` | `cost_sessions.jsonl` | 只有部分 summary 字段；assembly/traj 被丢 |
| `task_cm` | `runs/<genid>/cost.json` | task 子代事件汇总；空时 `absent` |

### 10.3 按运行时流程的传递链路

#### 链路 A：设计键 → 会话（进程内 plan/evaluate/self）

#### 链路 B：每轮 LLM 调用（装配 → 发送 → canonical 重建）

```text

  ├─ cm = 显式参数 > self.cm_session > None
  ├─ 若 cm.emit is None：绑到 trajectory_log.append(path)
  └─ chat_with_agent(..., cm=cm)
       ├─ cm.set_system_prefix(system_msg)     # dedup 目标
       ├─ cm.budget_reader = _cm_usage_reader  # 实付 meter
       ├─ cm.activate()                        # contextvar
       └─ 每个 LLM turn:
            _counting_llm
              ├─ cm.assemble_turn(raw_history, raw_msg, tokens_used, budget)
              │    ├─ turn += 1
              │    ├─ resolve(mode) → preset；或 _load_named() → run_assembly
              │    ├─ [passthrough] register_history/outgoing → emit_view → copies
              │    ├─ [slice] budget_checkpoint → window_defaults → dedup_prefix
              │    ├─ [compact] budget_checkpoint → conservative_compaction → window → dedup
              │    ├─ [custom] budget_checkpoint → window → dedup → run_policy
              │    └─ finalize_turn
              │         ├─ count_ops(records)
              │         ├─ emit_view(saved, records)
              │         └─ render(msgs) → 逐条浅拷贝
              ├─ kwargs["msg_history"] = send_history
              ├─ kwargs["msg"] = send_msg
              ├─ get_response_fn(**kwargs)       # llm.py 会 pop 副本的 key
              └─ canonical hist = raw_history + 新 entries（user 轮用 raw_msg 重建）
       └─ cm.deactivate()
```

#### 链路 C：工具面（`ctx_*` / policy）

```text
LLM 发起 tool call
  └─ llm_withtools.process_tool_call
       └─ ctx_* tool_function

                      └─ 失败：返回 {ok:False,error}；未变 view

```

#### 链路 D：审计/成本回流

```text
  ├─ [进程内 p/e/self] loop.log_event({**event, role}) 是默认 sink
```

#### 链路 E：driver 角色席位（当前断点）


## 11. 词表（术语 / 黑话 / 简称 / 指代）

### 11.1 阅读约定

- **“出现位置”**优先给代码路径/行号与文档小节；跨全仓使用的词写“全仓/本文件”。
- **“冲突/混淆”**只写真实会误导判断的差异；没有歧义的写“—”。
- 同一事物在本仓库常有“设计名 / 代码名 / 事件名 / 文档名”四套叫法，词表按“实际含义”归并，不按字面归并。

### 11.2 核心对象与模型

| 词条 | 出现位置 | 实际含义 | 涉及功能范围 | 冲突/混淆说明 |
|---|---|---|---|---|

## 12. L1 批次：整体接线 / 会话装配 / driver 适配（实现规划）

> 本章是 **L1（接线）批次**的规划与落地记录，对应 §4 的 L1 与问题 CM-01 / CM-02 / CM-07（seat 部分）。

### 12.0 已定决策（本批边界）

| 决策点 | 结论 | 理由/后果 |
|---|---|---|
| p/e 座位 CM 配置来源 | **父进程下发**（`role_state` 新增 `cm` 描述符），子进程只做本命名空间解析与构建 | `cost_keys_applied` 与真实会话同源；代价是 `role_state` 精确键集 + `_PROTOCOL_VERSION` 同步升版 |
| 会话摘要回流 | **事件通道**：子进程追加 `cm_session_summary`（events 路径 → 父进程转发落盘），`RoleProcess` 代理记住最后一条 | 不改 `_validated_result` 的三个精确字段集、不动三个 role 方法的返回契约；与 task 子代已有的 `cm_*` 事件聚合机制同构 |
| p/e 座位轨迹物化 | **本批不做**（CM-08 残项）。会话照常构建，历史切片/note/budget/`ctx_view` 全可用；父进程只下发子进程命名空间**可读**的轨迹文件，其余一次性发 `cm_traj_skipped` | plan/evaluate 座位看不见 task 轨迹（`output_dir` 只 bind 了该座位自己的轨迹根），物化需要换传输形态；轨迹读取继续走 `read_trajectory` 工具（本就经 broker） |
| Q4 六项加固 | **全部推后**，登记为接线后待办 | 见 §12.9 |
| 默认档位与失败门槛 | **保持 `passthrough` 默认 + 仅告警**（seeds/默认键不动，声称但构建不出只发 `cm_session_degraded`，不拒跑） | 行为零变化；`passthrough` 每轮仍发 `cm_view`，接线是否生效可从事件判断 |
| 验证通道 | 本机真实 driver smoke + 离线测试 | 环境已核对（§12.7） |

**纳入本批的两条“新链路自洽要求”**（不属于被推后的 Q4 加固）：

1. **stem 编码校验** `^[a-z][a-z0-9_]*$`（父进程与子进程两端各一次）。stem 现在要跨进程再参与路径拼接，不校验等于新链路自己开一个目录穿越面。
2. **cost 摘要白名单补齐** `assembly_active` / `assembly_failures` / `assembly_disabled` / `traj_segments`（`loop.py:_record_session_cost`）。不补则“摘要保真不了”：receipt 会读成 assembly 没跑过。

### 12.1 现状与目标

`gan/framework/role_process.py` 里 **grep 不到一个 `cm`**；loop 把 `cm_session` / `session_cm_mode` 挂在 `RoleProcess` 代理对象上（`loop.py:3096 / 3278 / 3589`），这是**不跨进程的死属性**。子进程内 `role.cm_session` 恒为 `None`，于是 p/e 座的 `ctx_index/ctx_fetch/ctx_budget/ctx_pin/ctx_note/ctx_view` 一律返回
`Error: no context-management session is active`，`cm_view` 事件为 0。

task 子代已接线，唯一缺陷是 sidecar 宿主权限（CM-02，run 树只读而 output 树可写）。

**本批目标**：p/e 座位的会话在子进程里真正建起来；装配侧解析按座位对齐；task sidecar 可追加。**不新增能力、不改默认行为。**

### 12.2 W1 — p/e 座位接线

**12.2.1 描述符（`role_state.cm`）**

| 字段 | 含义 | 谁算 |
|---|---|---|
| `keys` | 该 role 的 **clamped** `cm_*` 有效键（`effective_all` 的唯一 clamp 点仍在父进程） | loop `_effective_cost_keys` |
| `assembly_stem` / `policy_stem` | 设计命名的模块 **stem**（不是路径） | loop |
| `seat` | `plan` / `evaluate` / `self_improve` | loop |

| `session_cm_mode` | 喂 `AccessContext.session_cm_mode`（`read_trajectory` slice 前端档位） | loop |

`keys=null` → 子进程不建会话（与 in-process 语义一致）；整个 `cm=null` → 退化为今天的行为。

**12.2.2 子进程解析（`resolve_stem`）**

1. workspace 优先：`output_dir/workspaces/<role>/<instance>__<seat>/src/gan/components/<role>/cm/<stem>.py`
   —— 现有 `_resolve_cm_module` 用 `outer_<O>`，而实际授权目录是 `outer_<O>__<seat>`，**workspace-first 永远 miss**（CM-07 的一半）。
2. committed：`<code_root>/gan/components/<role>/cm/<stem>.py`（子进程看到自己的只读投影，投影确实含 `gan/components/<role>`）。
3. `evaluate` 座无 workspace（`role_broker` 的 `if seat != "evaluate"`），直接走 2。

**12.2.3 子进程构建**

- `role.session_cm_mode = cm.session_cm_mode`；`role.cm_session = build_from_descriptor(...)`
- `build_session(keys, policy_path, assembly_path, emit=<sink>)`；sink = 追加 events 路径（子进程里该 append 已被 `append_with_parent_event` 劫持转发为 IPC event → 父进程落 `events.jsonl`）。**与 in-process 的 `log_event` 同构**（今天 in-process 也是进 events.jsonl，不进轨迹），故不用 `emit=None`。
- 构建失败 → `cm_session_degraded{role, seat, reason}`（与 task 子代同一 loud fail-open 约定），不走异常路径。
- `base_role.run` 的 `chat_kwargs["cm"]` 无需改动：实例属性已在子进程内放好。

**12.2.4 摘要回流**

- 子进程在 `sink(...)` 返回后、`_purge_role_workspace` 之前追加
  `{"type":"cm_session_summary","role":…,"seat":…,"genid":…,"summary":<session.summary() 原样>}`

### 12.4 W3 — driver 适配（task sidecar 的位置）

**先更正本文件早期的两个判断**（原始审计写的是“可能 EACCES / 单文件 ACL 即可”）：
真实原因与文件权限无关，是**位置**问题，且分两层。两层叠在一起，才造成了那个
“绑定在、文件空、无任何报错、无 fallback 文件”的签名（CM-02）。

**第一层：harness 在自己的沙箱根里找 sidecar。**
`harness._sandbox_command` 的沙箱根是 **`stage_root`**（每题的 stage 副本），它却按
`os.path.isfile(<stage_root>/cm_events.jsonl)` 决定是否 `--bind`——而这份文件从来没人
放进 `stage_root`（`assemble_task_env` 把它预创建在 run 目录）。于是 bind 被**跳过**，
`/workspace/cm_events.jsonl` 不存在，子代**自己在 tmpfs 里创建**了它：所有 append
“成功”、没有异常、没有 fallback 文件，内容随沙箱退出蒸发。

**第二层（真凶）：回写目标在沙箱命名空间里不可写。**
即使把 sidecar stage 出来并 bind 成功，回写的目标仍是 `<run_dir>/cm_events.jsonl`。
但 harness 自己是**在沙箱命名空间内部**运行的：`_harness_bwrap_command` 里
`--ro-bind <run_fd> run_dir` + `--bind <output_fd> output_dir`（`task_execution.py:2128+`）。
对 run 树的写入因此是 **EROFS**，而 harness 的 stderr 在“题目成功”时被丢弃——
失败完全不可见。这就是为什么宿主机侧用真实 uid + `setfacl` 实测**能写**（那是在宿主
命名空间测的），而真实轮永远空。

**修法：把宿主文件放到沙箱内唯一可写的树（output 树）。**

- `paths.task_cm_events_path(run_dir, run_id)` = `<run_dir>/outputs/<run_id>/cm_events.jsonl`
  —— 唯一来源；`task_runner._ingest_cm_events(run_dir, run_id, genid)` 从这里 ingest 并删除。
- `harness.run_agent` 把 `<output_folder>/cm_events.jsonl` 作为 `cm_events_target` 传给
  `_run_sandboxed_agent`；后者 stage 一份**空** sidecar（属 sandbox uid）、`--bind` 到
  `/workspace/cm_events.jsonl`，并在每题结束后把 staged 内容**追加**回该路径
  （追加而非覆盖：一个 harness 进程回答多题）。
- `assemble_task_env` **不再预创建任何东西**在 run 目录，只 pin 沙箱路径
  `GAN_CM_EVENTS=/workspace/cm_events.jsonl`；task_broker 的静态 pin 不变。
- **回退了 `f9906b7` 给 run 树开的单文件 rw ACL 例外**（`_grant_cm_sidecar` 已删除）：
  run 树回到严格只读，“新文件不可创建”的 preflight 不变式保持绝对。
- 副作用检查：output 树就是 polyglot 的 workspace，`domains/task_worker._RUNTIME_SIDECARS`
  早已把 `cm_events.jsonl` 从 patch 的两条路径（scoped 与 `git add -A`）排除。

**确认无需改动**：`GAN_CM_*` 三个 env 白名单与 task_broker 静态 pin 已在位
（`test_task_env_mirror.py` 核对）；ingest 的 advisory 语义保持。

## §12.14 装配可信化：现状、问题、预期行为与决策（2026-11 批次）

> 本节承接 §12.12 的 S0–S9 分类结论：**装配可信化 = P0-c / P0 / P1 / P2 + 闩锁 + 反馈**。
> 目标不是"把 agent 当敌人"，而是把三件事分开：**可允许的自由面**（组合原语、`call_method`、
> 策略拒绝、自有记录）／**有兜底且可接受的少见情况**（异常、预算、未知方法、非 tuple）／
> **真问题**（静默失真：坏返回值、未记账视图、pin 被替代、canonical 被改）。

### §12.14.1 现状（改前）

| 面 | 事实 |
|---|---|
| 调用契约 | `assemble_turn` 只校验 `tuple(list, str)`——**元素级不查**（`[None]` 可进发送视图，`assembly_failures` 为 0） |
| 执行预算 | `run_assembly`/`run_policy` 用 `with ThreadPoolExecutor(...)`；`__exit__` = `shutdown(wait=True)` ⇒ 超时**只决定"何时判失败"，不约束本轮**。实测 `exec_ms=200` + `sleep(3)` ⇒ 本轮阻塞 **4.16s** |
| 后段记账 | `count_ops` 只信"传进来的 records"；`emit_view` 发 `ops` 简报（无内容）⇒ "视图被改但没记录"对审计是**不可见**的 |
| pin | ops 层拒绝替代 pinned；但**直接写 `session.view`** 可绕过（`dedup_prefix` 是最短反例：只省重复前缀，所以 **pin 终态允许 `full` 或 `dedup`**） |
| canonical | seam 传 `list(raw_history)`（**列表副本、条目同一批 dict**），LLM 返回后 canonical 由 `raw_history + new_entries` **按引用重建** ⇒ 原地改条目**永久污染**。替换成新对象则失效；改最后一条 user 文本会被框架还原成 RAW |
| 能力面 | 具名装配拿到的是**活 session**：可 `emit_view`/`count_ops`（伪造审计）、可赋值参数（抬 `max_ops_per_turn`）、可 `view.set`、可 `universe.register`、可 `_emit`——"cannot bypass the rules" 当时是**文档承诺**，不是事实 |
| 熔断 | 2 击、**每 call 独立**（session 是每次角色调用新建）、**不因成功归零**；与 policy 共用 `_POLICY_STRIKES = 2`（阈值有意同值、标识符无意共享 → 命名耦合债）；禁用后每轮 `cm_view.stats.assembly_disabled=true`（"不再尝试"持续可见） |

### §12.14.2 四项加固（P0-c → P0 → P1 → P2）

**P0-c（最优先，后果最重）执行预算真正约束本轮。** 两个 runner 改为显式池 + 超时后 `shutdown(wait=False, cancel_futures=True)` 再抛。
线程仍可能泄漏（Python 杀不掉线程 = CM-03 的独立问题），但**会话不再被拖住**。实测同一夹具 4.16s → **0.21s**。

**P0 返回值元素校验。** 新增 `_validate_sent_history`：元素必须是 dict、`role` 非空且在四个聊天角色内、`text`/`content`（若存在）必须是 str。
失败 = `AssemblyError(phase="contract")` → 与崩溃同一条响亮的回退路径。**不误伤**合法的"无文本载体"（`text`/`content` 缺省合法）。

**P1 轮末对账 + 回退到"上一个合法状态"。** 命名装配的轮首建快照（`view.forms/rules`、canonical 文本、计数、**已记账 ref 集**），轮末四项检查：

| 检查 | 捕获 | 说明 |
|---|---|---|
| `unrecorded_view` | 非 full 的 form 没有对应的已记账 op | 证据来源 = **handle `_audit`（成功的改动也记 refs）+ `count_ops`**，因为 form 是 **sticky** 的（第 2 轮的替换在第 3 轮仍是 non-full），所以 ref 集必须**会话级累计** |
| `pinned_form` | pinned 块的 form ∉ {`full`, `dedup`} | `dedup` 是最短反例（只省重复前缀），放行 |
| `canonical_mutated` | 条目文本与轮首不同 | 记录 `msgs[i]`，随后**恢复原文**。快照记 `(值, 载体键, 有无 text, 有无 content)`：**"给 `text` 条目 graft 一个 `content`"** 也必须被抓到并**删除该新增键**（`_msg_text` 优先读 `content`，只改回 `text` 等于没恢复） |
| `unclosed_turn` | 本轮改了视图却没走 `finalize_turn` | 文档内 API 就会踩（用了 handle、忘了把 records 交给 `finalize_turn`） |

违约时：`cm_assembly_violation{turn,kind,refs}` + 计数 → **恢复** → `AssemblyError(contract)` → preset 重跑本轮 + `degraded=true`。
**崩溃同样先恢复再回退**（崩溃路径也可能改了一半状态）。

回退目标是**上一个合法状态**（= 轮首快照），不是空白：空白会把前几轮的压缩成果全部作废，等于悄悄放大上下文并改变 pin 窗口/去重口径。
`universe` **不回退**（add-only 契约）：失败尝试注册的块/笔记不被任何 form 引用，发送内容干净，仅 `stats.blocks` 略大于干净重放。

**P2 `SessionPortal`（能力面收窄）。** agent 拥有的装配拿到的是门面而非活 session：

- **方法白名单**：`register_history` / `register_outgoing` / `budget_checkpoint` / `window_defaults` / `conservative_compaction` / `dedup_prefix` / `run_policy` / `call_method` / `finalize_turn` / `render`；
- **只读参数**：`mode` / `system_prefix` / `window_k` / `drop_floor_chars` / `min_compact_save` / `note_cap_chars` / `max_ops_per_turn` / `assembly_exec_ms` / `policy_exec_ms` / `turn`；
- **只读代理**：`view`（`form_of` + `forms`/`rules` 副本；无 `set`）、`universe`（`get`/`ordered`/`len`，返回**块副本**——块对象有 `pinned`/`msg_index` 等可变字段，给活对象就等于开后门）；
- **禁止**：`emit_view`、`count_ops`（后段**归 `finalize_turn` 独占**，也避免一次违约轮出现两条 `cm_view`）、`summary`、`_emit`、`_by_fp`、`_assembly_fn`、`assembly_active`、`_turn_degraded`、`methods_registry`、`notes`、任何 `_` 前缀；
- 访问被禁名/给参数赋值 → `AssemblyError(contract)`（不是裸 `AttributeError`，阶段归属清晰）；
- 参数名仍是 `session`（**签名不变**），只是对象变窄。

**逃逸仍是可能的**（`type(portal)`、闭包捕获）——那是**恶意层**，由 P1 对账兜底；门面把"半自愿的越界"从"默认可行"变成"必须先故意绕"。

### §12.14.3 熔断 → **指纹闩锁**（决策：首次失败即闩、四座统一）

取代"2 击"的理由：**复位条件不应该是计数，而应该是"配置真的变了"**。

- **状态**：`(role, seat) → {fp, stem, reason, phase, where}`；
- **指纹** = 有效 `cm_*` 键（clamped，已排序 JSON）+ 装配模块字节摘要，**workspace 优先 + committed 双候选**（两处都可被 agent 编辑）；
- **消费**：建会话前比对；一致 ⇒ 本会话**不加载模块**（descriptor 的 `assembly_disabled=true` / in-process 置位），每轮 `cm_view.stats.assembly_disabled` 仍可见；不一致 ⇒ **自动释放**（`cm_assembly_released` 事件）；
- **记录**：座位调用后读 summary，`assembly_failures > 0` ⇒ 闩锁（`cm_assembly_latched` 事件，带 stem/phase/where/reason）；
- **范围自然涌现**，不需要 per-outer 状态：p/e 的写者是**每 outer 一次的 self_improve** ⇒ 闩锁实际保持整个 outer；self_improve 同理；**task 座例外**：其会话由 task runner 构建（loop 不拥有该 config 路径），因此 task 座是**会话级**（每代最多 1 次尝试）——这正是"task 会话内保持回退 + 计划座可在本 outer 内修好它"的组合。
- **必要性诚实评估**：修完 P0-c 后熔断**与正确性无关**；它只限制"无意义重复尝试"的资源（泄漏线程 + 上界 CPU），本质是 **CM-03（无法终止）的临时代偿**，CM-03 落地后可降级为可选。

会话内仍保留一层**首次失败即闩**（`_ASSEMBLY_STRIKES = 1`，独立常量，不再借 `_POLICY_STRIKES`）：单会话不会每轮重试；跨会话由 loop 指纹闩锁接管。

### §12.14.4 反馈（"要求修正"的落地方式）

同一会话内**不做重试**（`_load_named` 是 load-once：改自己的模块不改自己的缝），所以"修正"发生在**下一个会话**，靠留痕 + prompt 提示：

- 事件：`cm_assembly_failed{phase, error, where, struck, fallback}`（`where` = 失败帧 `file:line`）、`cm_assembly_violation{kind, refs}`、`cm_assembly_latched` / `cm_assembly_released`；
- 会话 `summary()`：`assembly_violations` + `assembly_report{stem, phase, where, last_error, failures, violations, disabled}`（**只在真的失败过时出现**——缺席 = 模块没坏，不需要行动）；
- 下一个 self-improve 的 prompt 把 `assembly_report` 作为"待修事实"注入（与 `design_dangling_stripped` 同一风格）：
  loop 把它放进 self-improve 的 `recent["cm_assembly"]`（只在该 role 真的失败过时），
  **两个角色各自渲染一节** `## Your context-manager assembly (framework-measured; fix it with request_source_access + edit_source)`
  ——planner 走结构化 `recent` 的显式节、evaluator 走手写指令的显式节（它不整体 dump `recent`，所以必须单独加），
  二者内容都是**度量事实**（stem/phase/where/reason/latched），不是文本转储。

## §12.16 CM-03 残余批次：load 入预算 + 泄漏观测 + 席位 watchdog + 卫生重启（2026-11）

### §12.16.1 裁决依据（为什么 kill 不闩锁）

闩锁供血的盲区是"调用永不返回 → 无 summary → 闩锁收不到失败事实"。但 **load 入预算落地后 CM 已造不出
整调用挂死**：assembly load/assemble、policy load+apply 都在预算内有界失败（fail-open + 闩锁经 summary
正常供血）；agent 经 `ctx_*` 调用的死循环 METHOD 受工具分发超时约束（"本轮不等" + 每工具 wedge breaker，
`llm_withtools.process_tool_call`）。因此 watchdog kill 的成因几乎必然非 CM（工具死锁/LLM relay 失效/
child bug）——kill 即闩会把错误归因写进演化回路（健康的 agent 装配被禁用、下一个 self-improve 收到
"你的 assembly 失败了"的假事实）。`role_session_timeout` 事件附席位装配 stem 供诊断，不闩。
残留边缘（4 个不同工具并发 wedge 耗尽共享工具执行器 → 排队阻塞）输入相关、非系统性，由 watchdog 兜底收敛。

### §12.17.1 统一设计（M1+M3：共享实现与闩锁机器，独立生命周期）

- **共享**：`_ModuleLoad`（load-once 状态机：缓存成功与失败、限时加载、失败
  分类 crash/timeout）由 assembly 与 policy 各持一个实例；熔断统一为
  **1 击不清零**（`_AGENT_MODULE_STRIKES=1`，取代 `_ASSEMBLY_STRIKES=1` 与
  `_POLICY_STRIKES=2`）；指纹/闩锁表/consume/record 全部按 kind
  （assembly/policy）参数化，单份实现。
- **独立**：lazy 首载时机、缓存实例、事件词汇（`cm_assembly_*`/`cm_policy_*`
  保持分离——不同子系统不同状态）、反馈报告（`assembly_report`/`policy_report`）。
- **否决 M2（联合加载事务）**：激活条件不同（assembly 非passthrough 每轮、
  policy 仅 custom 尾部）——`mode=slice` + `cm_policy` 点名时 policy 永不运行，
  联合加载会让永不运行的模块的失败污染会话；演化独立（两个 stem 独立修复）；
  失败爆炸半径不同（去尾 vs 整轮）。
- **"load-once" 的契约表述：缓存的是模块，不是运行结果**——policy 的
  `apply` 仍每轮执行（`run_policy` 是 portal 方法，具名装配可调用）。

### §12.17.3 行为变化预告

1. policy 首次失败（load crash/timeout/run）即本会话禁用（原 2 击）；
2. policy load crash 计击并进闩锁/报告（原：不计击，下会话重试）；
3. assembly load crash 计击并进闩锁/报告（原：仅 fallback 事件，不计击）；
4. `cm_policy_failed` 至多每会话一条（原每轮可多条）；`cm_policy_disabled` 保留；
5. 自改 policy 文件的会话内热换消失（fixes 落到下一会话，由指纹变化释放闩锁）。
