## 二、二档清理（本次仅执行 R1、R3）

### R1 trajectory 可见性：删除死配置与死函数（方案 a）

**问题**：task 轨迹可见范围在 v4.20 起已完全由 loop 显式注入的
`AccessContext.trajectory_genids` 决定（plan → 直接父代；evaluate → 当前代 + 直接父代；
self_improve → 本 outer 全部 genid + 最后一代的直接父代），但 v0 时代的配置键与解析函数仍留在代码里，
且无任何消费者，制造了"可见范围可配置"的假象（文档还声称 "cap 默认 = loop.inner_max"，该联动从未实现）。

**改动**
- `gan/framework/loop.yaml`：删除整个 `trajectory:` 块（`parent_only` / `max_inner_generations`）。
- `gan/framework/trajectory.py`：删除 `visible_genids()`（全仓无调用）；模块 docstring 改为说明
  可见性由 `AccessContext.trajectory_genids` 显式决定。
- `AGENTS.md`：`loop.yaml` 条目更正为 "Task trajectory visibility is NOT configured here …"。
- `scripts/local/smoke_p1.py`：`test_trajectory` 中对 `visible_genids` 的断言随函数一并移除
  （连带删除该测试内变为未使用的 tree 构造与 import），其余断言不变。

**兼容性**：无配置消费者，删键不影响任何运行路径；旧 checkpoint 不受影响。

### R3 删除装饰性 RNG seed，并标注选择策略为确定性

**问题**：`GanLoop` 读取 `GAN_SEED` 环境变量并把 `seed` 存入 checkpoint（R5 曾声称 checkpoint
含 "RNG seed"），但整个 loop **没有任何随机源**——存取纯属装饰，且会误导读者以为存在随机化行为。

**改动**
- `gan/framework/loop.py`：删除 `_seed` 字段、`__init__` 中对 `GAN_SEED` 的读取、
  `_state_dict` 的 `"seed"` 键、`_load_state` 的恢复语句。

**选择策略标注（确定性）**
- 当前父代选择策略为**仅取 UCB 分数最高者，无随机**：`TreeStore.select_parents` 按
  `metric = score + ucb_c·sqrt(ln(N+1)/visits) − depth_penalty·depth − cost_penalty·cost`
  确定性排序取最高（visits = children+1；`cost_tokens` 目前恒为 None，该项实际为 0）；
  并列时由 Python `sorted` 稳定性决定（先入树者优先），**不含任何随机源（全文件无 `random` 使用）**。
  `tree.selection` 亦支持 `best` / `latest`，二者同为确定性策略。

**兼容性**：旧 checkpoint `state` 中残留的 `seed` 键在载入时被直接忽略（其余键照常恢复），
无需迁移；环境变量 `GAN_SEED` 不再被读取。

### R2 loop.yaml 无消费键清理（v5 讨论后执行）

**原则（已写入 `loop.yaml` 文件头注释）**：本文件每个键必须有代码消费者
（`cfg.get(...)`）；设计性陈述一律迁入 `AGENTS.md` / 本文档，不再以配置键形式存在。

**已删除的键（含理由）**

| 键 | 处置理由 |
|---|---|
| `schema_version`（顶层） | 无消费者（反馈/回执的 schema 版本各自硬编码于 `gan/summary.py`、`reward/packet.py`）；纯装饰性文件元数据 |
| `loop.trigger_outer_on_hard_failure` | **机制不实现，hard_failure 不中断内循环**（决策）。理由：信息通路已存在（penalties → 下一轮 planner prompt）；浪费上界由 `stagnation_patience` 兜住（最多多跑 1 代）；若以 evaluator 主观判断驱动控制流，会给 evaluator 新增"缩短内循环"的调度权（对抗面）。将来如需，应基于客观信号（`harness_rc` / `invalid_reason` / `contract_ok`） |
| `operators.max_ops_per_gen` / `operators.max_code_edits_per_gen` | `max_code_edits_per_gen`：**由架构保证**（每 inner 代收敛为单一 patch：多次授权副本进同一 workspace → 单一 diff → 单次 `apply_code_patch`），键冗余。`max_ops_per_gen`：**可做但暂不做**（见下）。二者防退化的作用实际由 `plan_max_tool_calls` 承担 |
| `source_access.default_mode` / `require_declaration` | **由构造保证**：默认面=配置+算子由工具集装配决定；源码物理隔离 + 唯一入口 `request_source_access` 即"先声明后传递"。语义迁入本文档 |
| `source_access.workspace_src_dir` | `access.py:src_dir()` 硬编码 `"src"`，全链路一致；无可配置价值 |
| `feedback.schema_version` / `mode` / `calibration` / `planner_sees` / `evaluator_sees` / `evaluator_sees_prev_feedback` | 整块删除；**信息流契约作为设计记录迁入下文**，运行时契约由三档 F1 以 smoke 断言锚定（枚举各会话实际注入字段），防止再漂移。连带改动：`smoke_gan.py` 原 `feedback.mode` 断言改为断言 `feedback` 键已不存在 |

**"可做但暂不做"（仅记录，本轮未实现）**
- **算子预算 `max_ops_per_gen`（N_op）**：定位是"进化卫生"（小步进化偏置）而非成本控制；若实测出现"单代设计改动过大"，先做三档 F8（告警 + 回执字段），硬拒绝（G4）靠后——硬拒会让模型烧轮次与门搏斗。注意 seed prompt 中原有一句字面 `N_op` 承诺，本次随键删除一并失效（该句从未被替换/执行）。
- **补丁大小上限**（单 patch 触及文件数）：**不做限制**（决策）。若将来需要，归 `code_repo.changed_files` 校验，而非本文件配置。

**feedback 信息流契约（设计记录；键已删，断言随 F1）**
- 反馈形态：**纯文字 digest**（issue → planner 回应 → 修复判定 + 证据），无数值权重；盲评偏差同样以文字记录，不作奖励项。
- planner 可见：evaluator issues（须逐条 `respond_issue`）、脱敏 diff summary、penalties、上一轮回执、父代摘要（含分数）。
- evaluator 可见：run_summary（blind 期剔除客观分/accuracy；注意 v5 审阅 A1——当前 `meta.records` / `receipt.grants` 仍可能夹带 planner 的 `reason`，待 F1 修复后契约才算成立）、反馈 digest、上一轮 issues（须逐条 `judge_fix`）、脱敏 diff summary、揭示后的 benchmark 分。

**`source_access.auto_approve` 的作用（键保留，接线待定）**
- 源码门控的**审批策略开关**。`AccessBroker(auto_approve=True)`（当前默认）= v0 语义"自动批准 + 全量审计"；`auto_approve=False` 时 `grant()` 直接 `raise PermissionError`（`access.py`）——**人工/外部审批的钩子已存在**，只是 `build.py` 尚未从本键读取（接线约 1 行）。
- 在接线前该键不产生任何运行时效果（与删除前一致）。是否接线（从而支持"每次深改需人工批准"的实验模式）**待定**；若决定永不接线，则下一批删键。

### 线 6（部分执行）：F6 `--domains` 单值透传（已实施；后被"续 2"修定）

> **勘误 #3（v5）**：下述"`--task-domain` 不一致时以 `--domains` 为准并告警"与
> "`--task-domain` 同步改写"语义已被"续 2"取代——`--task-domain` 参数已移除，
> `--domains` 成为唯一入口，多值在入口报错且不执行。以下原文仅作历史记录。

**语义（决策：暂不做多域）**：`--domains` 只接受**恰好一个**值；单值**权威**——
task_domain、task_brief、scores 标签三者统一为该域（`--task-domain` 与之不一致时以
`--domains` 为准并打印告警）；多值直接报错（"多域评测尚未实现"）。透传链
`run_gan.py → gan/driver.py → gan/outer_worker.py → build_gan_loop(domains=)`，
仅在提供时向 worker 追加 `--domains`（向后兼容）。

- `scripts/run_gan.py`：csv 解析（strip/去空）；单值校验（多值 `p.error`）；
  不一致覆盖告警；`--task-domain` 同步改写后传入 in-process 与 driver 两条路径。
- `gan/driver.py`：`run_gan_driver(..., domains=)`；程序化调用方再次校验单值；
  **未注册域名告警**（不在 `domains.yaml` 的 domains/families 中 → `domain_unregistered`
  事件，提示 brief/contract 回落 default）；`driver_start` 事件记录 `task_domain` 与 `domains`；
  worker 命令按需追加 `--domains`。
- `gan/outer_worker.py`：新增 `--domains`（同样单值校验）→ `build_gan_loop(domains=)`。
- 未来多域参照 DGM-H 模式（`generate_loop.py`：每代并行逐域评测 + `get_score` 按域存取 +
  `valid_parent` 全有才算 + `select_parent` 跨域平均，`gl_utils.py:511`）——四档量级另行立项。

/`runner.domain` 全部正确；`--domains search_arena --outer 0` → `driver_start{task_domain:
search_arena, domains:[search_arena]}`（search_arena 无 brief 为预期，v4.21 已记录）；

### 线 6（续）：G2-lite + G1-A（P1）+ F5 混合式 + 轨迹 attempt 分离（已实施）

**恢复政策（P1，最终措辞）**：resume 的恢复基线**只取最后一个完整 outer 边界**，
**不从崩溃的 outer 进行 resume**；不删除、不丢弃任何文件——崩溃 outer 的部分 ckpt、
其 gen 的节点/轨迹/分数全部保留在磁盘与 append-only 日志中可审计，仅退出恢复基线与
工作集（树经 `op=reset` 重建到边界快照）。附带一致性红利：code（checkout 到边界 commit）、
config（树快照的 `config_dict`）、tree 三者同时回退到同一状态。

- **G2-lite**：`checkpoint.save_checkpoint(..., code={"commit": <code_root HEAD>})`
  （`loop._save_checkpoint` 采集）；`_apply_self_patch` 成功后记 `self._role_commits[role]`
  并入 `_state_dict`（审计）。旧 ckpt 无 `code` 键 → 载入容忍（恢复时记
  `code_layer_absent` 事件并跳过校验）。
- **G1-A**：`run_gan_driver(..., resume, force)`；完成标记 = `ckpt/outer_<N>.json`
  （`latest_outer_index` 现成）。无 `--resume`/`--force` 且已有完成 outer → **拒绝重入**
  （RuntimeError 提示两个出口；决策：拒绝优于告警，防 UCB/树污染语义最清晰）。
  `--resume`：`start = latest+1`，跳过已完成 outer；worker 增 `--resume-boundary outer`
  → `run()` 的恢复目标由 `latest` 改为该边界（`resume` 事件记录 `boundary/attempt`）；
  driver 在 spawn worker **之前**比对 ckpt `code.commit` 与 code_root HEAD，
  不一致 → `code_repo.checkout` + `code_state_restored` 事件（崩溃窗口内的自改回退，
  git 历史与 `self_improve_commit` 事件保留）。`start > G` → `resume_complete` 事件后返回。
  `--force` = 显式逃生口，行为与旧版完全一致（legacy 重复风险自担）。
- **F5 混合式**：outer 编号快照规范名 `outer_<N>.json` **存在即跳过**（canonical 不可覆写，
  G1 完成标记语义不变）；同一 outer 重跑时另写归档 `outer_<N>_<毫秒时间戳>.json`
  （时间戳 = **ckpt 创建时刻**（写入墙钟，即 outer 完成时刻）——排序键是"哪一次拍的快照"，
  outer 开始时间属 attempt 语义、不入文件名）；payload 增 `completed_ts`。
  **勘误 #2（发现语义，v5 复审修正）**：发现逻辑必须同时覆盖规范名与归档名，且 **resume
  世系按时间取最新快照**（`newest_outer_snapshot`，按 `completed_ts`/mtime 排序），
  **start = 该快照的 outer index + 1**——而非"跨 N 取最大"：从中间 force 重跑会产生
  时间更新、编号更小的快照，按最大 N 会错误地跳回上一次运行的末尾
  （`latest_outer_index` 已移除；`_max_outer_index` 仅保留给 index 缺省时的防御性
  auto-assign，loop 恒显式传 index）。`load_checkpoint("outer")` 返回按时间的最新快照。
  遗留边界（记录）：`--force` 中途重跑后再 crash，恢复基线可能混 lineage——`--force`
  本身即声明自担的逃生口，支持路径是 `--resume`。
- **轨迹 attempt 分离**：`GanLoop` 生成 `attempt = uuid4().hex[:8]`（入 `_state_dict` 与
  `resume` 事件；每 worker 实例即新 attempt，不随 ckpt 恢复）；`_refresh_roles` 把 attempt

### 线 7：branch-per-node 代码血统治理（已实施）

**背景问题（审阅发现，均属实）**：
1. parent 的配置血统（`config_dict`）与代码血统断裂——patch 的 diff/apply 基线是
   code_root 的**时间线 HEAD**，而非 selected parent 的代码状态（`task_code_commit`
   仅作为记录、无任何恢复消费者）。
2. invalid child 的 patch 已 commit 进时间线主干，评测失败**无回滚**——污染后续
   planner diff 与所有后续 child 的运行代码。

**决策（参考 DGM-H 语义）**：
- **统一语义**：child 代码 = selected parent 的代码 + 本代 patch（与 DGM-H 的
  祖先链重放同构不变式）；**outer/inner 统一**——每代继承 selected parent 的
  全部仓库代码；outer 单链与 inner 树的差别只在 parent 选择方式（UCB 全树回选），
  不在 base 语义。
- **方案 A（决策）**：任务树跨 outer 完整继承、不重根不抛弃（branch-per-node 后
  跨 outer 回选成本 O(1)）。
- **实现选型**：branch-per-node（git DAG + 每 node ref）胜出 DGM-H 手动 patch
  重放（`git apply --reject` / `patch -p1` 静默跳 hunk 是硬伤；重放 O(depth)；
  patch 文件保留作 receipt 审计——血统交给 git parent 指针）。
- **覆盖度核实**："仅 commit + checkout"不安全——可达性靠 ref；每个 gen **必须**
  有轻量 ref `task_<genid>`（≈41B/个）。

**实施点**：

- `gan/framework/code_repo.py`（原语层）：`task_ref_name`/`outer_base_ref_name`
  命名单点；`ensure_branch`（不覆写：幂等/conflict）；`checkout_base`（**先解析
  SHA 再 checkout**——按分支名 checkout 会 attach HEAD 到锚 ref 上，后续 commit
  会前移锚 ref，必须避免）；`lineage_of`/`branch_tips`/`reconcile_refs`（对账只
  审计不阻断）；`apply_task_patch(...)`：对齐 base → 三重校验（不变）→ commit
  （git parent = base 的 commit，message `task gen <genid> parent <pid>`）→ pin
  `task_<genid>`；拒绝/空 patch → **alias base**（无空提交、无血统断点）。
- `gan/framework/loop.py`：`_pin_outer_base`（outer 开场把 HEAD 钉为
  `outer_<O>_base`，在 `--in-process` 与 worker 两种路径均生效）；`_resolve_base`
  （`initial → outer_<O>_base`，其余 = parent 的 `code_commit`，legacy 无记录 →
  HEAD 兜底 + `code_lineage_legacy`）；`_align_code_base`（**planner.plan 之前**
  checkout base + `code_lineage` 事件 + grant 文件 resync，`drop_missing` 防伪
  deletion diff）；resume 时 `reconcile_refs` 对账（`code_ref_missing`）。
- `gan/framework/task_runner.py`：`__call__(..., base=)`；meta 新增
  `base_commit/code_commit/code_ref_ok/code_ref_mode`；`task_code_commit` 保留
  且改语义为**恒填**（无 patch/rejected = base）。
- **语义保持**：outer 快照 `code.commit` 仍 = 快拍瞬时 HEAD；role self-patch 仍
  落主线 HEAD 不建分支；invalid child 不回滚 git（死分支可审计，base 只从 valid
  parent 的 ref 解析）。
- legacy 兼容：老节点无 `code_commit` → base=HEAD + `code_lineage_legacy`（行为
  等同旧版）；ref 缺失 → `code_ref_missing`（不阻断）。

**验证（离线）**：`scripts/local/test_kinship.py`（ref 幂等/冲突、DAG 血统、
分叉内容隔离、rejected/no-patch alias base、reconcile 报告）；见"三、验证"。

## 五、线 4 专项：子进程沙箱实现复杂度评估（记录；本轮未实施）

### 5.1 本机可行性实测

| 探测 | 结果 | 含义 |
|---|---|---|
| 环境 | WSL2 / kernel 6.6.87.2 / 当前 root | — |
| `bwrap` 安装与 `--ro-bind/--tmpfs/--proc/--dev` | 可用 | L2 路线无需装包 |
| userns + mount ns（`unshare --user --map-root-user --mount`） | 可用；无 Ubuntu 24.04 的 apparmor userns 限制 sysctl | bwrap 内核前提满足 |
| `--unshare-net` | 可用 | 网络隔离可行 |
| **Landlock** ABI 探测 | **EINVAL，不可用**（内核未启用该 LSM） | 该路线出局 |
| Docker | CLI 在，daemon 当前不可达（Desktop 未运行；docs/1 证实时可用） | 容器路线依赖外部状态 |
| `bwrap --unshare-user --uid 65534` 后读 `/root` 与数据集 | **照样读到** | **userns 的 `--uid` 是假降权**（命名空间内映射，宿主 DAC 仍 root）——标准陷阱，已实测 |
| `setpriv --reuid 65534`（宿主真 setuid）后 | `/root`(0700) 与数据集 csv 全部 Permission denied | **真降权有效**；当前唯一挡板是 `/root` 0700（环境脆弱点：仓库本体 755，换部署位置即失效） |

### 5.2 问题拆分与对 V4.14 的两点修正

沙箱实为三个难度迥异的问题：**① 标签泄漏**（已触发：一次浅层 `select_component("skills","bash")` 即可让 task 拿到 bash，`GAN_DATASET_ROOT` 指向 repo）、**② 越权读写**、**③ 网络/凭证外传**（最贵）。

- **修正 1**：V4.14 "只对 bash 做工具级沙箱"的前提是 LLM 在父进程——这对 p/e 成立，但 **task 的 LLM 与工具都在同一子进程内**（harness 直接 litellm）。task 侧必须**整进程隔离**；工具级包装只对将来 p/e 开放 bash 时有意义。
- **修正 2**：触发条件已**对 task 侧实质满足**（浅层 bash 路径）；p/e 侧仍未满足（无 bash），维持暂缓。

### 5.3 方案阶梯（复杂度 × 防护 × 改动面）

| 方案 | 防住 | 防不住 | 改动面 | 工作量 |
|---|---|---|---|---|

| **L1.5 真降权 uid**：宿主 setuid 专用用户 + chown run copy/输出 + `NO_NEW_PRIVS` | ①②（本机 /root 0700 下仓库整体不可读） | ③；隔离强度依赖 `/root` 0700（脆弱点）；多域资产在 /root 下需显式拷入 run copy | `task_runner` 启动 + setup + 资产清点 | 0.5–1 天（paper_review） |
| **L2 bwrap 整进程**：真 setuid + bwrap（收窄 fs 视图 + net 隔离 + die-with-parent），**per-domain profile 入 `domains.yaml`** | ①②③ | 内核逃逸面（userns）；GPU 域需显式 bind（`/dev/dxg`、`/usr/lib/wsl`） | 封装 wrapper + profile 矩阵 | paper_review 1–2 天；全域 2–4 天 |

| **L3 工具级 bwrap**（仅未来 p/e bash；bash 组件外包一层） | 与 L2 同（局部） | — | 1 个文件 | 半天（前提已验证） |

### 5.4 凭证困境与 G3 协同

task 子进程必须自调 LLM → 必持 API key（run copy 内有 `.env`），bash 可用时 key 即可读——**③ 与标签无关地存在**。彻底解法 = **LLM 父进程代理**（子进程只指向本地端点）：凭证不出父进程、网络出站收敛、且所有调用过代理 → **G3 成本记账的天然挂点**。属架构级改动，**不单独为沙箱做，与 G3 合并决策**。

### 5.5 结论与路线

- 复杂度排序（低→高）：**L1.5 ≈ L1 < L2 < L2.5 ≪ LLM 代理**；Landlock 出局。
- 建议路线：立即以 **B5（bash/editor 移出 task 可选面或加防线）止血** → **G6a(L1) + G6b(L1.5) 叠加**（合计 2–3 天，线 4 泄漏路径即便保留 bash 也不成立）→ **G6c(L2)** 按域渐进 → Docker 仅多依赖域；LLM 代理并入 G3。
