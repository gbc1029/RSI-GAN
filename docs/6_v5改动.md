## 二、二档清理（本次仅执行 R1、R3）

### R1 trajectory 可见性：删除死配置与死函数（方案 a）

**问题**：task 轨迹可见范围在 v4.20 起已完全由 loop 显式注入的
`AccessContext.trajectory_genids` 决定（plan → 直接父代；evaluate → 当前代 + 直接父代；
self_improve → 本 outer 全部 genid + 最后一代的直接父代），但 v0 时代的配置键与解析函数仍留在代码里，
且无任何消费者，制造了"可见范围可配置"的假象（文档还声称 "cap 默认 = loop.inner_max"，该联动从未实现）。

**改动**
- `gan/framework/loop.yaml`：删除整个 `trajectory:` 块（`parent_only` / `max_inner_generations`）。
- `gan/framework/trajectory.py`：删除 `visible_genids()`（全仓无调用）；模块 docstring 改为说明
  可见性由 `AccessContext.trajectory_genids` 显式决定。
- `AGENTS.md`：`loop.yaml` 条目更正为 "Task trajectory visibility is NOT configured here …"。
- `scripts/local/smoke_p1.py`：`test_trajectory` 中对 `visible_genids` 的断言随函数一并移除
  （连带删除该测试内变为未使用的 tree 构造与 import），其余断言不变。

**兼容性**：无配置消费者，删键不影响任何运行路径；旧 checkpoint 不受影响。

### R3 删除装饰性 RNG seed，并标注选择策略为确定性

**问题**：`GanLoop` 读取 `GAN_SEED` 环境变量并把 `seed` 存入 checkpoint（R5 曾声称 checkpoint
含 "RNG seed"），但整个 loop **没有任何随机源**——存取纯属装饰，且会误导读者以为存在随机化行为。

**改动**
- `gan/framework/loop.py`：删除 `_seed` 字段、`__init__` 中对 `GAN_SEED` 的读取、
  `_state_dict` 的 `"seed"` 键、`_load_state` 的恢复语句。

**选择策略标注（确定性）**
- 当前父代选择策略为**仅取 UCB 分数最高者，无随机**：`TreeStore.select_parents` 按
  `metric = score + ucb_c·sqrt(ln(N+1)/visits) − depth_penalty·depth − cost_penalty·cost`
  确定性排序取最高（visits = children+1；`cost_tokens` 目前恒为 None，该项实际为 0）；
  并列时由 Python `sorted` 稳定性决定（先入树者优先），**不含任何随机源（全文件无 `random` 使用）**。
  `tree.selection` 亦支持 `best` / `latest`，二者同为确定性策略。

**兼容性**：旧 checkpoint `state` 中残留的 `seed` 键在载入时被直接忽略（其余键照常恢复），
无需迁移；环境变量 `GAN_SEED` 不再被读取。

### R2 loop.yaml 无消费键清理（v5 讨论后执行）

**原则（已写入 `loop.yaml` 文件头注释）**：本文件每个键必须有代码消费者
（`cfg.get(...)`）；设计性陈述一律迁入 `AGENTS.md` / 本文档，不再以配置键形式存在。

**已删除的键（含理由）**

| 键 | 处置理由 |
|---|---|
| `schema_version`（顶层） | 无消费者（反馈/回执的 schema 版本各自硬编码于 `gan/summary.py`、`reward/packet.py`）；纯装饰性文件元数据 |
| `loop.trigger_outer_on_hard_failure` | **机制不实现，hard_failure 不中断内循环**（决策）。理由：信息通路已存在（penalties → 下一轮 planner prompt）；浪费上界由 `stagnation_patience` 兜住（最多多跑 1 代）；若以 evaluator 主观判断驱动控制流，会给 evaluator 新增"缩短内循环"的调度权（对抗面）。将来如需，应基于客观信号（`harness_rc` / `invalid_reason` / `contract_ok`） |
| `operators.max_ops_per_gen` / `operators.max_code_edits_per_gen` | `max_code_edits_per_gen`：**由架构保证**（每 inner 代收敛为单一 patch：多次授权副本进同一 workspace → 单一 diff → 单次 `apply_code_patch`），键冗余。`max_ops_per_gen`：**可做但暂不做**（见下）。二者防退化的作用实际由 `plan_max_tool_calls` 承担 |
| `source_access.default_mode` / `require_declaration` | **由构造保证**：默认面=配置+算子由工具集装配决定；源码物理隔离 + 唯一入口 `request_source_access` 即"先声明后传递"。语义迁入本文档 |
| `source_access.workspace_src_dir` | `access.py:src_dir()` 硬编码 `"src"`，全链路一致；无可配置价值 |
| `feedback.schema_version` / `mode` / `calibration` / `planner_sees` / `evaluator_sees` / `evaluator_sees_prev_feedback` | 整块删除；**信息流契约作为设计记录迁入下文**，运行时契约由三档 F1 以 smoke 断言锚定（枚举各会话实际注入字段），防止再漂移。连带改动：`smoke_gan.py` 原 `feedback.mode` 断言改为断言 `feedback` 键已不存在 |

**"可做但暂不做"（仅记录，本轮未实现）**
- **算子预算 `max_ops_per_gen`（N_op）**：定位是"进化卫生"（小步进化偏置）而非成本控制；若实测出现"单代设计改动过大"，先做三档 F8（告警 + 回执字段），硬拒绝（G4）靠后——硬拒会让模型烧轮次与门搏斗。注意 seed prompt 中原有一句字面 `N_op` 承诺，本次随键删除一并失效（该句从未被替换/执行）。
- **补丁大小上限**（单 patch 触及文件数）：**不做限制**（决策）。若将来需要，归 `code_repo.changed_files` 校验，而非本文件配置。

**feedback 信息流契约（设计记录；键已删，断言随 F1）**
- 反馈形态：**纯文字 digest**（issue → planner 回应 → 修复判定 + 证据），无数值权重；盲评偏差同样以文字记录，不作奖励项。
- planner 可见：evaluator issues（须逐条 `respond_issue`）、脱敏 diff summary、penalties、上一轮回执、父代摘要（含分数）。
- evaluator 可见：run_summary（blind 期剔除客观分/accuracy；注意 v5 审阅 A1——当前 `meta.records` / `receipt.grants` 仍可能夹带 planner 的 `reason`，待 F1 修复后契约才算成立）、反馈 digest、上一轮 issues（须逐条 `judge_fix`）、脱敏 diff summary、揭示后的 benchmark 分。

**`source_access.auto_approve` 的作用（键保留，接线待定）**
- 源码门控的**审批策略开关**。`AccessBroker(auto_approve=True)`（当前默认）= v0 语义"自动批准 + 全量审计"；`auto_approve=False` 时 `grant()` 直接 `raise PermissionError`（`access.py`）——**人工/外部审批的钩子已存在**，只是 `build.py` 尚未从本键读取（接线约 1 行）。
- 在接线前该键不产生任何运行时效果（与删除前一致）。是否接线（从而支持"每次深改需人工批准"的实验模式）**待定**；若决定永不接线，则下一批删键。
