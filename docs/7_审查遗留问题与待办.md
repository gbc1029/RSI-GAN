## 1. 沙箱与运行隔离（独立栏）

> 全部位于 `domains/harness.py`（bwrap 沙箱路径）与其调用方 `gan/framework/task_execution.py`。
> **背景**：v5/fix1 已把"基准标签仅经 CLI `--dataset_root` 传给父 harness"落地（子进程 env 剔除 `GAN_DATASET_ROOT`），这一栏是**该次改造之后**仍然存在的问题。

### S1 — `--unshare-all` 后跟 `--share-net`，网络实际未隔离 `未披露` `中`

- **现象**：`domains/harness.py:78-79` 连续出现 `"--unshare-all",` 与 `"--share-net",`。bubblewrap 选项按出现顺序生效，`--share-net` 的语义是"**不** unshare 网络命名空间"，因此它把 `--unshare-all` 隐含的网络 unshare 重新关掉 → 沙箱与宿主共享网络。
- **触发**：任何沙箱路径运行（task agent 具备 `bash`/`editor` 技能时可直接外连）。
- **旁证**：`docs/6_v5改动.md` 6.4 节自己记录了 `httpx.get → 200`（网络本身连通）；第五节 G6c 计划里的 `--unshare-net` 并未落地。
- **修法**：删除 `--share-net`（保留 `--unshare-all`），或显式写 `--unshare-net`。

### S2 — 每题子进程无 `timeout=` `未披露` `中`

- **现象**：`domains/harness.py:159-166` 的 `subprocess.run(...)` **未传** `timeout=`；对比 `gan/framework/task_execution.py:148` 的外层 `timeout=timeout`。
- **后果**：单题挂死会阻塞整个 `ThreadPoolExecutor`（`:298-317` 退出时等所有 future），整代只在外层 1800s 被杀；而 `predictions.csv` 仅在 `save_interval` 边界（`:334-337`）或最终（`:341`）落盘 → **一次挂死可丢掉整代已有结果**。
- **触发形态**：子进程无响应（`docs/6` 6.4 已记录的"缺 `OPENAI_API_BASE` 时长挂"即此形态）。
- **修法**：给 `subprocess.run` 加 per-question timeout；并把失败记录与 predictions 一并纳入 `save_interval` 落盘。

### S3 — 结果 sentinel 可被 task agent 伪造 `未披露` `中`

- **现象**：结果通过从子进程 stdout 反向匹配前缀行解析（`domains/harness.py:170-173`），前缀 `__RSI_TASK_RESULT__` 是仓库内公开常量（`harness.py:19`、`domains/task_worker.py:11`）。
- **后果**：task agent 或其工具只要打印一行 `__RSI_TASK_RESULT__{...}` 即可**劫持判定结果**。这是信任边界的位置错误（把"子进程 stdout"当作可信通道）。
- **修法**：改用私有 sentinel 文件（沙箱内只写、父进程读），或 sentinel 携带随机 token。

### S4 — 5 处 bind 源无存在性守卫 `未披露` `中`

- **现象**：`domains/harness.py:107-113` 对 `agent_host` / `agent/` / `utils/` / `domains/__init__.py` / `domains/task_worker.py` 的 `--ro-bind`/`--bind` **无 `os.path.exists` 守卫**；只有 `.gan_runtime`（`:118-123`）改成了条件 bind。
- **后果**：上游拷贝清单（`task_execution.py:38-45` 的 `_RUNTIME_FILES`/`_RUNTIME_DIRS`/`_HARNESS_FILES`）与 bwrap 命令一旦不同步，bwrap 直接 `Can't find source path` 非零退出。**这与 `docs/6` 6.2 节记录的两个 bug 属同一类**，只是当前这几项恰好都存在。
- **修法**：统一加存在性守卫（缺文件时给出可读错误），或把拷贝清单与 bind 清单收敛为同一个常量来源。

### S5 — `eval_failures.jsonl` 以 `"w"` 打开 `未披露` `低`

- **现象**：`domains/harness.py:345` `open(..., "w", ...)`。
- **后果**：resume 复跑会**覆盖**上一次的失败记录；且 `save_interval` 中途落盘（`:334-337`）只写 predictions、不写 failures，进程在最终块前被杀则失败记录不落盘。
- **修法**：改 `"a"`，并把 failures 与 predictions 同频落盘。

### S6 — `resume_from` 越界时每题失败 `未披露` `低`

- **现象**：`resume_from` 时 `output_folder = os.path.abspath(resume_from)`（`harness.py:250`），而沙箱用 `run_root = os.path.realpath(os.getcwd())` 做包含性校验（`:141-143`、`_sandbox_path` `:36-45`）。`--resume_from` 指向 cwd 之外时，`chat_history_*.jsonl` 不在 `run_root` 下 → 抛 `ValueError` → **每一题都被记为失败**。
- **触发**：`python -m domains.harness --dataset_root R --resume_from /abs/elsewhere`。GAN 路径恒用 `--run_id`，**不触发**，属潜在缺陷。
- **修法**：统一 `abspath`/`realpath`，或对 `resume_from` 放宽包含性要求。

### S7 — 凭证经 env 进入沙箱 `未披露` `低`

- **现象**：`domains/harness.py:155` `child_env = dict(os.environ)` 把父进程**整个环境**传给沙箱子进程，仅剔除 `GAN_DATASET_ROOT`/`PYTHONHOME`/`PYTHONPATH`/`OLDPWD` 四项（`:156-157`）。因此 `OPENAI_API_KEY` / `OPENAI_API_BASE` 等**经 env 进入沙箱**。
- **文档矛盾**：`docs/6` 6.4 节前半句称"child 按 fix1 设计又不挂载 `.env`（**凭证不进沙箱**，正确）"，与 `harness.py:155` 的实际行为矛盾（同节后文自己承认"凭证仍经父进程 env 下发"）。
- **修法**：改为白名单式 env（只传沙箱内真正需要的变量）；同时修正 6.4 节的措辞。

## 2. 反馈与血统链路

> 根因：**循环本地状态（`self._last_feedback` / `_last_receipt` / `_prev_predicted` / `_prev_benchmark`）与树式父选择（parent 的 `meta`）两套语义并存**。fix1 只把 planner 切到后者。

### L1 — fix1 半修：evaluator 与 digest 结算仍读循环本地 `未披露` `中`

- **已修的一半**：planner 读所选 parent 的 meta —— `loop.py:688-692`（`parent_feedback`/`parent_receipt`/`parent_predicted_score`/`parent_benchmark_score`）、`:700`（`last_feedback=parent_feedback`）、`:707`（`receipt=parent_receipt`）。
- **未修的一半**：evaluator 仍拿循环本地 —— `loop.py:772` `"receipt": self._last_receipt`、`:774` `prev_feedback={**(self._last_feedback or {}), "digest": self._last_digest}`；结算同理 —— `_settle_feedback_digest`（`loop.py:171-189`）用 `self._last_feedback` / `self._prev_predicted` / `self._prev_benchmark`。
- **后果**：当 UCB 选中的 parent ≠ 上一轮 child（`tree.branch_limit=2` 之后完全可能）时，planner 回应的是 parent 的问题，evaluator 却在评判"上一轮循环"的问题，digest 又把 parent 的 responses 与循环本地的 issues 配对（`issue_id` 对不上 → 被记为"silently ignored by planner"）。
- **修法**：`evaluate` 的 `prev_feedback`/`receipt` 与 `_settle_feedback_digest` 一并改读**所选 parent 的 meta**，使三个消费方语义一致。

### L2 — planner 的 `records` 与 `receipt.grants.reason` 仍流向 evaluator `已披露(F1)` `中`

- **现象**：`task_runner.py:207` 把 `records` 写进 `child.meta`（含 `request_source_access` 的自由文本 `reason`）；`loop.py:772` 把 `receipt`（其 `grants` 含 `reason`）塞进 `run_summary`。`loop.meta_view` 只排除 `report_summary`/`delta_vs_parent`，**未排除 `records`**。
- **性质**：提示注入 / 泄漏通道（planner 的 rationale 应经 `summary.build_diff_summary` 脱敏后可见）。
- **修法**：`meta_view` 扩白名单并排除 `records`；`receipt.grants` 去掉 `reason`。

### L3 — `_last_receipt`/`_last_self_receipt` 不随 checkpoint 持久 `已披露(F3/F4)` `低`

- **现象**：`_state_dict` 无此二键（`loop.py:88` 等），故 resume 后上一轮回执丢失，下一轮 planner/evaluator 收不到回执。
- **修法**：纳入 `_state_dict`/`_restore`（与 L1 一起做，避免语义再分叉）。

### L4 — `build_diff_summary` 解析的是废弃算子 `已披露(R4)` `低`

- **现象**：`gan/summary.py:24,28,31,34,36` 处理 `tune_param`/`apply_config`/`set_tool_enabled`/`swap_module`/`add_config`/`code_edit`；现行设计算子 `set_config`/`set_param`/`select_component`/`deselect_component` **无字段提取** → evaluator 只看到 `{"op": "select_component"}` 空壳。
- **修法**：把 op 分支更新为现行算子（保留旧分支以兼容历史记录）。

## 3. 回执与审计信号

### A1 — 空补丁被记为"补丁被拒" `未披露` `中`

- **链路**：
  1. `gan/framework/task_runner.py:115-116`：`if task_code_commit == base_commit and task_code_commit: task_patch_rejected = "no new code commit (patch rejected or absent)"` —— 只要**没有新提交**就置该字段，**包含"本轮根本没提出补丁"这一绝大多数正常情形**；
  2. `task_runner.py:206` 写入 `child.meta["task_patch_rejected"]`；
  3. `loop.py:435` `rejected = plan_result.get("patch_rejection") or child.meta.get("task_patch_rejected")` → **恒为真**；
  4. `loop.py:469-472` 记事件 `{"type": "receipt", ..., "rejected": true}` → **每代 `events.jsonl` 都报 rejected**；
  5. `receipt.py:94` + `43-58`：`_next_hint()` 对**任意非空** reason 返回兜底串 `"Fix the reported problem, then stop; do not repeat the same action."`；
  6. `receipt.py:121-122`：只要该字段非空就追加 `hint: …`（**不要求补丁曾被提出**）；
  7. `gan/roles/planner.py` 的 `plan()` 用 `render_receipt(receipt)` 注入下一轮 instruction。
- **后果**：无深改的代，planner 提示词里出现 `## Previous round receipt` + `- hint: Fix the reported problem, then stop; …`，凭空暗示"有问题待修"；同时审计流每代记 `rejected: true`。
- **修法**：区分"未提出补丁"与"补丁被拒"（仅后者置 `task_patch_rejected`），或让 `_next_hint` 在无补丁时返回 `""`。

### A2 — invalid 代不写 `scores.jsonl` `已披露(F7)` `低`

- **现象**：`_archive_invalid` 路径不调用 `_append_score`，故评测失败的代在分数索引中不可见（权威证据仍在 `runs/<genid>/`）。
- **修法**：为 invalid 代写一条 `score_status="invalid"` 记录。

## 5. 设计面与种子接线

- **后果**：`seeds/task.md` 里 "Solve the given task as well as you can… produce your final answer in the required output format" 这段**从未到达 task agent**。
- **待决选项**：
  - **(a) 接线**：`_initial_task_config()` 改用 `load_seed("task")`。代价：改变进化起点（影响与历史 run 的可比性）；且该文本与 `task_agent.py` 的 instruction 模板（已含 "Respond in JSON format…"）**重复**。

  - **(c) 保留 + 注明**"预留/未接线"。
  - **倾向 (b)**，除非确认要让新 run 有更丰富的起点。

### G2 — seed 修改只影响新 run（运营注意，非缺陷）`低`

### G3 — `frozen.py:61-62` 注释措辞误导（待确认）`未披露` `低`

- **原文**：`Explicit trust anchor (documentation / defence-in-depth). NOT used for the allowlist decision, but the gate asserts nothing here is ever granted.`
- **核对**：`frozen.py:104` `return not _matches(rel, TRUST_ANCHOR)` —— `is_allowed` **确实**把 TRUST_ANCHOR 当额外拒绝过滤器；`frozen.py:133-135` `deny_paths()` 返回它，`gan/build.py:120` 传入 `AccessBroker`，由 `gan/framework/access.py:181` 消费 —— 它**还是**一份运行期拒绝清单。
- **结论**：**不是逻辑错误，是措辞误导**。"NOT used for the allowlist decision" 在最窄读法（`ACCESS` 白名单不含它）下成立；但 "(documentation / defence-in-depth)" 会让人以为它不参与判定。今天效果为空（这些路径本就不在任何角色白名单内，属冗余防线）。**风险**：信任锚文件里一条与实现相反的注释，会诱导后人"改代码去匹配注释"，从而删掉一层防御。
- **建议文本**（1 行改动，待确认后应用）：
  ```python
  # Explicit trust anchor. NOT part of the ACCESS allowlist (no role lists it), but
  # enforced as an extra deny filter in is_allowed() below and passed to the broker
  ```
